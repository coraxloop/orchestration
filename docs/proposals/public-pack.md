# Public pack contract · `proposal:publicpack:public-pack-contract`

Status: PROPOSED — this document defines the publication boundary and the acceptance contract for a reusable orchestration pack.

## The generality boundary · `sec:publicpack:generality-boundary`

The public tree is the reusable system. It contains models, policies, specifications, packages, infrastructure artifacts whose configuration is expressed by placeholders or typed inputs, fictional examples, setup guides, and the declarations needed to check those materials. It may describe roles, constraints, schemas, and classes of deployment, but it does not record which values one installation currently assigns to them.

`local/` is the estate instance. It contains the live server and account registry, the backlog, rollout and recovery plans, release records, machine and orchestrator overlays, pack burn values, and recipes whose truth depends on one installation. Secrets remain outside Git even when the non-secret record that refers to their custody belongs under `local/`.

A line may live outside `local/` only when it would remain true and safe after the repository was installed on another estate with different machines, people, providers, accounts, addresses, and filesystem layout. A real server, account, superloop, person, provider coordinate, network address or port, allocation or expiry identifier, and workstation or server path fails this test. A placeholder whose type is explained passes, as does an alias from the explicitly fictional register in `docs/examples/`; an example is not generic merely because its real value looks ordinary.

The boundary applies to every tracked byte, including comments, defaults, diagnostics, captured command lines, expected fixtures, reference implementations, manifests, and generated documents. Historical provenance does not excuse an instance value in the public tree; provenance that matters to this estate moves with the value into `local/`, while a reusable argument is restated without the value.

## The rulebook split · `sec:publicpack:rulebook-split`

The machine rulebook and orchestrator rulebook are deployed as one complete document apiece, but their repository sources should have two authorities. Each root rulebook remains a generic base containing stable constraints, audience boundaries, and references to typed operational values; a corresponding `local/rulebooks/` overlay contains the machine profile, toolbox and SDK inventory, concrete paths, worker roster and thresholds, superloop identity, and current door. `docs/examples/rulebooks/` supplies complete fictional overlays so a pack recipient can see the required shape without receiving the publishing estate's values.

Assembly occurs only at installation. A Rust install primitive reads one base and one validated overlay, renders a deterministic single document, enforces unique section keys and the declared order, and hands the rendered bytes to the content-diffed copy transaction. The transaction compares the complete rendered target, preserves an equal target and its modification stamp, backs up outgoing bytes before replacement, applies the declared mode, and produces one watched-rulebook change event. Meson owns invocation and the tagged target map once the maintained installation graph lands; neither concatenation in a shell script nor a manual copy can satisfy the installation contract.

The orchestrator hook's 9,500-byte limit applies to the rendered `ORCHESTRATION.md`, not just its base. The renderer therefore measures the final bytes before mutation, the base reserves an explicit overlay budget, and an oversize result fails without touching the installed target. A tag must already identify the reviewed base, renderer, example, overlay schema, and target map before any installation build or mutation begins.

This shape is preferable to a template with scattered scalar substitutions. The dynamic material includes ordered tables and operating paragraphs rather than a small stable field set, so named interpolation slots would either become an untyped second language or force instance prose back into the base. A validated overlay keeps each fact under one authority, allows complete review, and still yields the single deployed document required by instruction discovery.

A pack recipient receives both generic bases, the overlay schema, and complete fictional overlays. The recipient copies the examples into `local/rulebooks/`, replaces every fictional value from its own registries, validates the overlays, and installs only after selecting a reviewed milestone tag.

## Code and fixtures · `sec:publicpack:code-and-fixtures`

Released code has no default that selects a live endpoint, account, checkout, toolchain setup file, wrapper path, or state root. A required value is read from a typed command argument, environment contract, install-generated configuration, or the current registry; a convenience default is permitted only when it is portable or explicitly fictional and cannot contact a live system. Missing operational configuration fails before transport or mutation.

The lane verifier must therefore stop naming a real SSH alias and concrete server paths in its defaults. Its tests inject a complete fictional server profile using aliases from `docs/examples/servers.md`, fictional filesystem roots, and a fictional workstation user; expected SSH argument and input fixtures change with that profile. Explicitly supplying the former values must continue to produce the same transport, output bytes, exit meanings, and state effects until a separately ratified behavior change says otherwise.

The staff-provision key-generation module must not contain an SSH configuration block with a fixed server roster or endpoint coordinates. It receives the alias-only configuration shape through typed input or an adapter over the current registry, renders only the entries requested by that input, and never accepts, constructs, prints, or persists a raw address or transport port. Its tests and documentation use the same fictional alias register as the rest of the public tree and a fictional loop and workstation identity.

Changing an expected fixture is contract-visible because reviewers use committed captures to see the bytes a caller observes. It is not automatically an external-contract change: the external stability rule protects streams, framing, exit meanings, reports, and state effects, while selection of a default alias or checkout is configuration. The genericization lane proves this distinction by testing old behavior under explicit injected configuration, new failure behavior when required configuration is absent, and fictional default or example bytes without changing the governed reports.

## Enforcement — the burn list · `sec:publicpack:enforcement-burn-list`

The linter gains a public-pack burn family whose zero state is enforced by the root check. Its public policy declaration defines the recognizer and the public surface; its instance values live in `local/linter/public-pack-burn.toml`, because placing the values themselves under `.linter/` would reproduce the leak the policy exists to prevent. Each value declares either substring matching for paths, coordinates, domains, and sufficiently specific aliases, or ASCII-identifier-boundary matching for short names; the latter refuses an ASCII letter immediately adjacent to the value while still finding its standalone, hyphenated, and underscored forms, so an unrelated longer word cannot create a false hit. The initial set is the closed census recorded in the estate rollout plan: the workstation login and owner e-mail domains, every live server and account alias, live superloop and door identities, site subnet stems, live provider coordinates and identifiers, estate-only checkout and home paths, concrete server checkout/toolchain/wrapper paths, and any live identity found reused as a fixture.

The current configuration model first takes the declared universe, subtracts the global ignore relation, and assigns each surviving path exactly once through `.linter/owners.toml`; `.linter/policies.toml` then activates owner-policy pairs, policy documents declare prose and code surfaces with path patterns, and `.linter/lists.toml` holds the exact per-file burn ratchets. A surface rooted at `.` is repository-wide rather than clipped to the activating owner's share. Public-pack enforcement specializes that model with a policy-local exclusion for `local/`: the root-wide scan sees every other partition, while the local partition remains owned and checked by all unrelated policies.

This specialization requires two linter changes rather than a global ignore. Burn surfaces need an explicit exclusion relation so `local/` can be omitted from this family alone, and the declared snapshot needs a first-class public-pack mode in which the local partition has zero reach and the instance burn-value document is absent. Absence in that mode is declared behavior, not a compatibility fallback; a normal estate checkout still requires the local value document and fails atomically if it is missing or malformed.

The register is maintained with the registry, not after a leak. A commit that adds or renames a live server, account, superloop, provider coordinate, allocation, workstation root, or other distinguishing value adds its literal to the local burn register in the same commit and proves that the public census remains zero. A removal may delete a literal only after history and retained release policy no longer require it as a regression guard; ordinary remediation changes per-file occurrence counts toward zero and never transfers an occurrence between files.

Because a pack cannot contain the publishing estate's literal register, the release manifest records its digest and declared-token count. Pack acceptance runs the non-vacuous burn scan over the extracted public tree with that source-side register supplied as read-only verifier input, while the recipient's later estate checkout supplies its own local register.

## The pack itself · `sec:publicpack:pack-itself`

A public pack is one ZIP containing the public tree from one reviewed milestone tag, a provenance manifest naming that tag, its resolved commit, and its tree hash, and the fictional examples including the rulebook overlay. It contains no `local/` path, no working-tree bytes, no Git metadata, and no generated artifact that was not bound to the same tag. The manifest may additionally record the pack-format version, archive digest, linter version, burn-register digest and token count, and acceptance results; these fields do not replace the required source identities.

The archive command of record is the exclusion pathspec already established by the repository: `git archive TAG -- . ':!local'`. Release substitutes the fixed reviewed tag for an ambient branch or mutable `HEAD`, verifies that the tag resolves to the reviewed commit before and after packaging, and uses Git's object database so ignored, untracked, and locally modified bytes cannot enter. The provenance manifest is generated from that same resolved object and added at `docs/public-pack-provenance.toml` as an explicit virtual archive member, where the documentation partition owns it; the final ZIP is then hashed and the manifest copy retained with the release record.

A direct owner invocation of `git archive` is a release recipe, not a maintained shell helper. If publication requires a repeatable one-command implementation, a Rust `pack` subcommand belongs in a dedicated `packages/public-pack` package, invoked by the Meson release target; it resolves and rechecks the tag through typed Git arguments, renders the manifest, writes the ZIP without a shell trampoline, extracts to a disk-backed staging directory, and runs the acceptance probes before publishing the digest.

A recipient extracts into an empty directory, reads the public setup guide, copies the fictional overlay to `local/`, replaces example data with its registry values, establishes the local burn register, and uses the tagged installation path. Example aliases are never edited in place inside `docs/examples/`; they remain the stable public fixture world against which packages are tested.

## Verification · `sec:publicpack:verification`

Every genericization bite has a narrow probe for its document family or package, followed by the root check and a search for the literals it removes. Package changes build and test only their owning package on a registered worker server; fixture changes additionally compare the complete expected bytes, and rulebook changes render and size-check both fictional and estate overlays without installing them.

The pack acceptance gate extracts the ZIP into an empty disk-backed directory and proves three conditions. First, the root check passes with `local/` absent; the harness creates an inert Git index over the extracted members so the declared `tracked-exclusive` universe, which takes the tracked base and holds the checkout to it after declared ignores, remains meaningful without importing history, and the owner partition and snapshot loader must accept a zero-reach local row and absent local overlay in declared public-pack mode. Second, a burn scan using the source-side literal register named by the manifest finds zero occurrences in every extracted member. Third, the exact extracted workspace builds package-scoped on a registered worker server, with source identity and returned evidence bound to the manifest commit and treated under the ordinary server trust boundary.

These three proofs are the acceptance gate for every later bite: standalone root conformance, a non-vacuous zero burn census, and server-side package buildability. A missing local tolerance, unowned provenance member, changed archive identity, absent burn input, skipped package, or server/source mismatch blocks the pack and therefore blocks the release tag.

## Open questions · `sec:publicpack:open-questions`

1. **Does the machine rulebook belong in the pack?** The options are to retain `CLAUDE.md` as the generic installable base with a local machine overlay, or to move the deployed source wholly into `local/` and publish only a non-installed guide under `docs/`. The lean is to retain the generic base: its audience and stable safety rules are reusable, the installer already owns the deployed target, and the example overlay makes the required specialization visible without publishing one machine's profile.
2. **What happens to `install.sh` before Meson installation lands?** The options are to keep it as the live installer until a complete Meson/Rust replacement exists, to document manual copies, or to retire it at the rulebook split. The lean is to keep it only as historical behavior source while the split waits for the complete Rust install primitive and tagged Meson target map; manual copying cannot prove content comparison, backup, mode, unchanged modification time, or the one-event rule, and teaching the script to assemble would create a prohibited maintained shell path.
3. **Do local plans need another fictional example?** The options are to treat `docs/examples/plans/backlog.md` as sufficient, to add one complete fictional rollout plan, or to mirror every local plan family. The lean is to add a single fictional rollout only when the setup guide relies on a plan-specific schema not already demonstrated by the backlog and server examples; mirroring instance history would create maintenance debt without improving the pack contract.
