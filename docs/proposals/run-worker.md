# Worker launcher · `proposal:runworker:per-worker-uid-launcher`

The agent-side watching and waiting recipes retained below, including fresh-agent, never-resume, listener and session-side polling instructions, are superseded by (`proto:dispatch:log-eater-callback`) and (`proto:dispatch:heartbeat-supervision`); program interfaces, historical observations and quoted former instructions remain as recorded.

Status: DRAFT — this proposes a package that does not exist. Nothing here installs, launches, or changes a live loop; the first bite and its acceptance are named at the end.

## Purpose · `sec:runworker:purpose`

`run-worker` gives every dispatched lane a uid of its own. Today a lane is a clone under the estate's temporary root and a driver process, both at the same uid as the session that dispatched them and as every other lane of every other loop; what keeps one lane out of another's tree, out of its loop's private material, and off its loop's hub is the lane's brief and the permission gate reading it. Both are worth having and neither is a boundary the kernel knows about, so neither reaches a driver the gate never sees or a process the brief never addressed. A lane that runs at its own uid is bounded by the modes of the files around it, on every open, for every process it starts, whether or not anything classified the request.

The launcher exists because that boundary cannot be built by the thing it bounds. Allocating a uid, owning a tree to it, dropping to it, and reclaiming it afterwards are acts of a principal above the worker; they happen inside the owner's user namespace as namespace root, which is the one privilege in this estate that can hand ownership across uids. Putting them in a reviewed binary with an exact-argv planner is what keeps that privilege in one auditable place rather than spread across dispatch scripts. The permission-triage design this serves is in [permission triage](permission-triage.md), whose deployment section states what the gate needs from each tier; this document states how the third tier is built.

## Namespace and uid mechanics · `sec:runworker:namespace-and-uid-mechanics`

The mechanics are the entry command's, and `run-worker` reuses them rather than inventing a second way to cross a uid boundary — with one field changed, which is named here rather than left to be discovered. Every crossing today is one `podman unshare sh -c OUTER-SCRIPT`: the outer script copies `/etc/passwd` and `/etc/group` into a temporary directory, appends a line naming the target uid, creates an empty `ssh_config.d`, and invokes a nested `unshare -m sh -c INNER-SCRIPT sh "$t"` (`packages/loop-home/src/planner.rs:127-137`). The inner script bind-mounts the three temporary paths over `/etc/passwd`, `/etc/group`, and `/etc/ssh/ssh_config.d`, then executes `setpriv --reuid=UID --regid=UID --clear-groups env -i` with `HOME`, `USER`, `LOGNAME`, `SHELL`, `PATH`, `TERM`, `LANG`, `TMPDIR`, and the five XDG variables before the caller's command (`planner.rs:110-126`). Ownership changes use the same outer privilege without the drop: `podman unshare chown -R UID:UID PATH` and `podman unshare chmod MODE PATH` (`planner.rs:188-216`).

Four of those pieces are measured requirements rather than decoration, and a launcher that dropped any of them would fail the way the entry command already failed once: the clean environment exists because caller variables leaked in and made Git warn on every command, the temporary passwd entry exists because an unmapped uid has no name and SSH exits immediately, the empty bind-mounted `ssh_config.d` exists because SSH refuses configuration fragments it reads as unowned inside the namespace, and the nested mount namespace exists because a mount made directly under `podman unshare` persisted in the rootless namespace afterwards.

**The drop is where a worker differs from a loop, and the difference is load-bearing.** A loop's entry drops one principal into one group: `--regid=UID` makes the primary group the loop's own uid and `--clear-groups` empties the supplementary list, and the group line the outer script appends is `NAME:x:UID:` with no members (`planner.rs:131`). Composed unchanged for a worker uid that would leave the worker in no loop group at all, and every group-mediated path the tier layout depends on — the shared rubric, the shared login, the lane's own tree, the loop's estate outbox — would be closed by the kernel. A worker's drop is therefore `setpriv --reuid=WORKER_UID --regid=WORKER_GID --groups=LOOP_GID --no-new-privs env -i …`, where `WORKER_GID` equals the worker's own uid and `LOOP_GID` is named numerically so membership does not depend on a member list being right. The temporary group file gains a line for each of the two gids so that tools resolving them by name find one. The two groups are different on purpose: the loop's group means "every lane of this loop" and gates what the loop shares with all of them, while the lane's own gid means "this lane alone" and gates its tree and, by default, every file it creates. Making the loop's group primary would collapse the two and hand each lane read access to its siblings' trees.

`--no-new-privs` is the second addition and it is what makes the paragraph below true rather than merely asserted. A process that has dropped cannot come back: `setpriv --reuid` sets the real, effective, and saved uids, and re-entering the owner's user namespace requires a capability in it that the dropped uid does not hold. But an exec can still raise privilege where a set-user-ID file or a file capability is reachable, and the estate tree's `hooks/` directory is world-executable by design because every worker's hook must run from it. Setting `no_new_privs` at the drop makes the kernel refuse set-user-ID, set-group-ID, and file capabilities across every later exec in that process tree, so "final for the life of the process and for every process it starts" describes the kernel's behaviour rather than an expectation about what happens to be installed.

## Uid allocation · `sec:runworker:uid-allocation`

Each loop's registry entry declares its worker block as `LOOP_WORKER_UIDS=BASE:COUNT`, an inclusive run of uids reserved to that loop's lanes. The launcher allocates the lowest free slot in its loop's block and refuses when the block is full; deployment validation requires every declared block to be disjoint from every other block, from every registered `LOOP_UID`, and from the deployment uid.

Disjointness is not the only check the block needs. Owning a tree to a uid and dropping to it work only for uids the owner's user namespace maps, and that mapping is built from the deployment account's entries in `/etc/subuid` and `/etc/subgid`. A block validated against a compiled range can therefore pass at deployment and fail at `chown` or `setpriv` when a lane launches, which is the worst moment for it: after a tree exists and before anything runs. Validation reads both files for the deployment account and requires every uid in the block, and the gids beside it, to be no greater than the count of the deployment account's subordinate range, because a rootless namespace maps that range onto namespace ids 1 through the count and every number this design writes — the loop uids, the worker blocks — is a namespace-internal one. Both counts are read, because the two files are configured separately and a gid beyond the subordinate gid count fails exactly as an unmapped uid does. With the estate's proposed scheme of 256 slots from base 40000 in steps of 256, the last block whose top stays inside 65535 has base 65088: 99 loops, which is the number a validator can check.

The block is declared rather than derived, and the alternative is worth naming because it looks cheaper. A derivation — a worker's uid computed from its loop's uid by a fixed stride — needs no field and no validation, and its safety property is that no two loops can collide. But that property would then rest on an arithmetic invariant nothing checks, held by a numbering convention compiled into a binary, over an estate whose loop uids were assigned by hand. A declared block is checked pairwise at deployment exactly as state roots already are, and the estate writes its numbering where it already writes its numbering.

Which slot is live is the launcher's own record, `runs/table.tsv` in the loop's public run tree: one row per live lane, naming uid, lane, driver, commit, and start time, written only by the launcher and readable by everyone. That table is evidence and not authority. The gate resolves a worker's loop from the registered block its effective uid falls in, so a stale or damaged table changes a journal field and no decision, and a loop cannot name a uid the estate did not first give it.

## Subcommand contract · `sec:runworker:subcommand-contract`

```text
run-worker prepare LOOP LANE COMMIT
run-worker launch LOOP LANE --driver claude|codex [--budget SECONDS] [--model M] [--effort E]
run-worker watch LOOP LANE [--stall SECONDS]
run-worker fetch LOOP LANE
run-worker close LOOP LANE
```

|Subcommand|Runs as|Does|
|----------|-------|----|
|`prepare`|the deployment account|Allocates the lane's uid and claims its row in `runs/table.tsv` under the table's own lock, creates `workers/LANE/` loop-owned at 0750 in the loop's own group, clones the hub into `workers/LANE/clone` at `COMMIT`, sets the lane's local git identity with signing off, drops the remote, writes the brief beside the clone, and records the clone's resolved head in the row. The principal is the deployment account rather than the loop because every path it creates is installed through the owner's user namespace, which only that account can enter.|
|`launch`|the deployment account, with the child dropped to the worker uid|Fills the claimed row's driver and start instant under the same lock, re-groups the `workers/LANE/` that `prepare` made to the allocated lane's gid, creates the monitor's lock in it, owns the clone and the home's writable children to the worker, writes `identity.env`, registers the hook in the worker's settings, drops the child, and executes the driver with the run directory. The parent stays at namespace root as the monitor. The re-group happens here because this is where every mode and ownership command runs, after the tree is built and before the drop.|
|`watch`|the loop uid|Blocks until the run report, an escalation, a stall, or the budget, and returns which of those happened.|
|`fetch`|namespace root, then the loop uid|Re-owns the lane's clone to the loop, then fetches the worker's branch from it as a local path into the loop's quarantined candidate ref. The re-own is required rather than tidy: the clone is 0700 at the worker's uid, and the loop is neither its owner nor in its group, so a fetch at the loop uid without it fails on the open before git's own ownership refusal is reached. The re-own is one-way, so `fetch` ends the lane rather than sampling it: afterwards the clone is the loop's and the worker cannot write it, which is correct at the point a branch leaves and wrong at any earlier one.|
|`close`|namespace root, then the loop uid|Reaps anything still running at the worker uid, re-owns or archives that lane's outbox files, removes the worker tree, moves the run directory aside, removes the table row, and frees the slot.|

There is no `adjudicate`. An earlier draft had one, writing a disposition a worker's hook would consume on retry; the deployed one-shot approval path reads the journal rather than a disposition tree, refuses any caller that is not an orchestrator, and refuses an approval whose source event was not an orchestrator's, so that subcommand would have needed three implemented refusals lifted before it could do anything. The route that exists is the one the gate already documents: the worker's suspicious request is journaled and denied, `watch` reports it, and the loop's main session re-issues the approved work as its own request, marking its own journal with the review command at the deployment uid. The launcher's part in that is the waiter, and the waiter it already has.

Exit codes are the estate's, and `watch` distinguishes its four outcomes because the superloop arms it as a background waiter and the harness notification is the callback: 0 the step published its run report, 3 an escalation is waiting for the loop, 5 the budget was exhausted and the child was stopped, 42 the step is stalled, 4 a refusal decided before any privileged call, 2 a usage refusal, 1 a runtime failure. The stalled status is 42 because that is already the declared stalled status of the estate's run-directory watcher, and one number meaning one thing across two readers is worth more than a fresh number meaning it here.

Every subcommand writes one evidence line naming what it did and ends on standard output with the estate's terminal report in the published field order, `RUN-REPORT exit=STATUS wall=SECONDS.MILLISs verdict=VERDICT`, so a lane's launch is timed the way every other action in this estate is timed. `launch` additionally reports the allocated uid and the run directory, because those two values are what every later subcommand and every reader needs.

## Directory layout · `sec:runworker:directory-layout`

|Path|Owner|Group|Mode|Contents|
|----|-----|-----|----|--------|
|`LOOP_HOME`|loop|loop|0711|The four subtrees below; traversable by every uid and enumerable by none.|
|`LOOP_HOME/private/`|loop|loop|0700|The loop's clone, memory, keys, and its own journal work. Closed to the worker entirely.|
|`LOOP_HOME/shared/`|loop|loop|0750|What the loop hands its workers, and nothing else.|
|`LOOP_HOME/shared/permissions/domain.md`|loop|loop|0640|The worker rubric, read at the exact path `identity.env` names.|
|`LOOP_HOME/shared/logins/`|loop|loop|1770|The Claude credentials directory and the link to the shared Codex sign-in, files at 0660. The one write grant.|
|`LOOP_HOME/workers/`|loop|loop|0710|One directory per live lane; the group traverses and cannot enumerate.|
|`LOOP_HOME/workers/LANE/`|loop|that lane's gid|0750|The lane's tree. Loop-owned so the lane cannot unlink what is inside it.|
|`LOOP_HOME/workers/LANE/clone`|worker|that lane's gid|0700|The lane clone, owned by the worker so the lane can commit in it.|
|`LOOP_HOME/workers/LANE/home/`|loop|that lane's gid|0750|The worker home, with the harness's writable children pre-created at the worker's uid. Loop-owned for the same reason `workers/LANE/` is: write permission on a directory is the permission to rename what is inside it, so a worker-owned home would let the lane move `.claude/` aside and run with no hook registered.|
|`LOOP_HOME/workers/LANE/identity.env`, `brief.md`|loop|that lane's gid|0640|Lane, loop, uid, gids, role, run directory, rubric path; and the brief.|
|`LOOP_HOME/workers/LANE/home/.claude/`|loop|that lane's gid|0750|Settings and the hook instance at 0640.|
|`LOOP_HOME/workers/LANE/monitor.lock`|loop|that lane's gid|0640|The monitor's lock, created before the drop.|
|`LOOP_HOME/runs/`|loop|loop|0755|One run directory per live lane, `table.tsv`, and the closed-run archive.|
|`LOOP_HOME/runs/UID/`|worker|that lane's gid|0755|Events, output, last message, run report, kill evidence, and the worker's escalation journal.|

Three rows carry decisions rather than conventions. `workers/LANE/` is owned by the loop and not by the lane, because ownership of a directory is the permission to unlink what is inside it: a lane that owned its own tree could remove the `identity.env` that names it, the brief it is measured against, or the settings that register the classifier hook — the three files there whose whole purpose is to be beyond it. Its group is the lane's own gid rather than the loop's, because every lane of a loop shares the loop's supplementary group, so a loop-grouped lane tree would be readable by every sibling lane. And `runs/` and `workers/` have stated modes at all because every traversal in this design passes through them; an unstated intermediate mode would close a path the rows beneath it assume is open.

The run directory is named by uid rather than by lane because the gate must derive it from facts it already holds — the registered `LOOP_HOME` and the caller's effective uid — and a root read out of a file the caller can write is a caller-supplied root, which the journal contract forbids for the reason it forbids every caller-supplied path. The lane name is inside the directory, in the table, and in the run report, so nothing a reader needs is lost; `close` renames the finished directory to `runs/closed/LANE-UID-STAMP/`, which is the lane-named path a human or a log reader wants and is also what keeps a reused uid from ever appending into a dead lane's evidence.

## What it links and what it copies · `sec:runworker:links-and-copies`

The worker home links the loop's Claude credentials directory and the link to the shared Codex sign-in; it copies neither. A copied credential is a second secret with its own lifetime, its own revocation, and nothing tracking it, and the account it authenticates to is one account either way — several lane homes signed into one account already share one rate-limit window. A link means the loop's single sign-in is the single sign-in, and removing it removes it everywhere at once.

A link alone is not enough, and the reason is a property of the harness rather than of this design: the harness rewrites its stored login when a token refreshes. A read-only link therefore fails at the refresh boundary, which means every lane long enough to reach one. `shared/logins/` at 1770 with its files at 0660 is the answer, and it is the single write grant a worker holds inside its loop's tree — stated here and in the tier layout rather than left implicit in a mode. It adds a denial surface and no escalation: a principal that can read a token can already use it, so replacing it means being able to break the loop's sign-in, not to exceed it. The sticky bit that stops the symlink swap also stops a rename-over, so the refresh must write in place.

The worker charter and the classifier hook are links into the estate tree, for the same reason in the other direction: a redeploy of the rules reaches every live worker, and no worker holds a private copy of the text it is judged by. The brief is a copy, because it is the lane's input and must not change underneath a running lane; a brief that changed mid-run would make the lane's report unauditable against it.

Nothing in the worker home reaches a hub. `prepare` clones from the hub at the loop uid and then drops the remote, because a remote a worker has no key for is an affordance that fails as an authentication error instead of as a refusal. The branch leaves the clone by `fetch`, which re-owns the clone to the loop and then reads it as a local path at the loop uid.

## Trust argument · `sec:runworker:trust-argument`

What a worker can reach: its own clone and home, its own run directory, its loop's `shared/` subtree — the worker rubric to read and the logins to read and rewrite — the estate tree's world-readable rules and binaries, and its loop's estate outbox as a drop box it can add to and not remove from. What it cannot reach: the loop's `private/` tree at all, the loop's git and signing keys, the loop's hub, the loop's memory, the loop's journal, any sibling lane's tree or its brief, any other loop's home, and namespace root. None of that depends on the permission gate, on the worker's brief, or on the driver behaving.

There is no per-worker credential and the design does not want one. A Claude worker authenticates as its loop, which is the one sign-in the loop has; inventing a second would add a secret to provision, rotate, and revoke while changing nothing about which account is billed or rate-limited. The residual is therefore exact and should be stated as such: a compromised worker can spend its loop's model quota, can act as its loop toward the model provider, and can break its loop's sign-in by corrupting the file it is allowed to refresh. It cannot push, cannot sign, cannot authenticate to any server, and cannot read anything the loop did not place in `shared/`.

One boundary inside the worker home is load-bearing and easy to lose. If the worker could rewrite its own settings it could unregister the classifier hook, and the gate inside the worker tier would be decorative. Loop ownership of `workers/LANE/`, of `home/`, and of `home/.claude/` is what prevents it — not the 0640 on the settings file, which would be defeated by unlinking it from a directory the worker owned, and not loop ownership of `.claude/` alone, which would be defeated by renaming it out of a home the worker owned. The obligation this creates is named rather than hidden: the launcher pre-creates the harness's writable children at the worker's uid, and a harness version that wants one the launcher did not create fails with a permission error, which is loud and repairable, and is the correct direction for that failure to point.

## Failure modes · `sec:runworker:failure-modes`

**Block exhaustion.** `launch` refuses with a usage status when its loop's block is full. A block sized well above a loop's concurrent lanes makes exhaustion mean a leak rather than a busy day, so the refusal is a diagnosis: some earlier lane was never closed, and its row in the table names it.

**The monitor's own privilege.** The monitor is the parent of the drop, and that parent is namespace root — the deployment uid outside the namespace, uid 0 inside it — not the loop uid. Saying otherwise would be wrong in a way that matters twice over: only namespace root can signal a process at another uid, so the reaper could not reap if it were the loop; and a lock the monitor must write could not live in a worker-owned directory if it were. This is the one long-lived namespace-root process in the design, so its surface is deliberately small: it creates the monitor's lock in the `workers/LANE/` that `prepare` made, before the drop, and thereafter reads sizes, modification times, and the lifecycle's own marker lines, enforces the budget, and signals. It executes nothing from the worker's tree and interprets no content the worker wrote.

**A dead monitor over a live child.** The lock names the monitor on its first line and the child on its second, so a reader finding a dead holder whose child is alive knows the step is still running and must not be settled — the durable lifecycle contract already reads a lock exactly this way, and `watch`, at the loop uid, reads it as the owner of both the lock and `workers/LANE/`, since that directory's group is the lane's own gid and the loop is not in it. Recovery is `close`, which can reap by uid.

**A worker that outlives its budget.** The monitor stops the child at the budget with the ordinary kill evidence. If the monitor is gone too, the uid is the handle: everything running at a worker's uid belongs to that lane and nothing else does, so killing by uid is both correct and complete. That is a reaper a shared uid cannot have, and it is one of the two reasons per-lane uids are worth their cost — the other being that a peer lane cannot edit the commit this lane is about to ship.

**A successor inheriting a predecessor's evidence.** The sticky bit on the loop's estate outbox stops a concurrent peer and does nothing about time: a uid freed on close and allocated again would leave the next lane owning its predecessor's 0644 outbox files, free to unlink them. So `close` re-owns that lane's outbox files to the loop uid, or moves them under a closed prefix, before it frees the slot — the same protection the run directory already gets from its rename, applied to the one other place a lane's evidence lives.

**A crash between owning and dropping.** The order is allocate, build the tree at the loop uid, own it to the worker, then drop; a crash anywhere leaves a tree owned by a uid with nothing running as it, which `close` reclaims and which no other principal can use in the meantime.

**A `close` against a live lane.** It reaps first and then removes, and reports what it killed. A `close` that found a live child says so in its evidence line, because a lane silently reaped during an import is a lost report.

## Tests · `sec:runworker:tests`

Unit tests use the model the estate's other namespace-crossing binaries use: pure planners turn a validated registry record and arguments into exact argv, and an injected runner owns every external command, so no test invokes podman. A fake namespace shim stands in for the outer and inner scripts, recording the argv it was handed and performing the ownership and mode changes the plan asked for, at the test's own uid and under a test root. That shim proves the layout, the modes, the ordering, and the refusals; it cannot prove that a different uid is refused, because a test process has only one uid.

|Layer|Cases|Evidence|
|-----|-----|--------|
|Credentials|Exact drop argv for a worker: `--reuid` the allocated uid, `--regid` its own gid, `--groups` the loop gid numerically, `--no-new-privs` present; both gid lines in the temporary group file; no `--clear-groups`|The one field that differs from the entry command is asserted rather than inherited.|
|Allocation|Free slot, full block, block overlapping a peer, block overlapping a loop uid, block outside a fixture subordinate uid range, gids outside a fixture subordinate gid range, reuse after close|The lowest free slot is taken; an unmapped or overlapping block is refused before any command runs.|
|Entry planner|Exact outer and inner scripts for a worker uid, quoting of a home and a command containing a space and a single quote|Byte-stable composition against the entry command's measured requirements.|
|Layout builder|Every row of the layout table, loop ownership of `workers/LANE/`, of `home/`, and of `home/.claude/`, the lane's gid set on `workers/LANE/` after allocation, pre-created harness children, `identity.env` contents and mode, lock created before the drop|Each path is created with its stated owner, group, and mode, in the stated order, with the ownership change last.|
|Subcommand contract|Each subcommand's evidence and report lines, each `watch` outcome and its status, refusals before any privileged call|Status and report bytes are asserted against a scripted runner.|
|Close|Live child reaped, outbox files re-owned or archived, table row removed, run directory renamed, slot freed|A reused uid owns neither its predecessor's run directory nor its outbox files.|

The acceptance is one real launch. A read-back lane is prepared, launched at a real worker uid, and its first reply read; the run directory is read at the deployment uid without entering anything; the loop's `private/` tree and a sibling lane's tree are each proved unreadable from the worker's uid while `shared/` is proved readable and its login directory writable; and the lane is closed and its slot reused. Unit fixtures cannot authorize that step and do not claim to — the uid separation is the entire claim, and only a real uid tests it.

## First bite · `sec:runworker:first-bite`

`prepare`, `launch`, and `watch` for the Claude driver, and nothing else. Files: a new `packages/run-worker` with its planner, layout builder, allocator, runner, binary, README, and tests. Shape: the allocation rules including the subordinate-mapping check, the entry composition with the worker's credentials and `--no-new-privs`, the layout table, `identity.env`, the hook registration, and the four `watch` outcomes. Tests as above, each failing before the change, with the acceptance launch held as a separate step that the bite's gate does not perform.

`fetch` and `close` follow in a second bite, because each depends on a loop-side path the permission-triage deployment is still placing — the quarantined candidate ref, the closed-run naming, and the outbox sweep — and a launcher that guessed any of them would have to be rewritten when they land. Until it lands, a lane launched by the first bite is reclaimed by hand, which is a bounded cost while exactly one loop is migrated and a reason not to migrate a second before it does. That deferral is also why the estate runs staggered for the length of the migration, which the deployment section states where it matters: a loop that has not moved still dispatches lanes that resolve to no identity at all.
