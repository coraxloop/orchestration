# Permission triage · `proposal:permissiontriage:rubric-driven-model-gate`

Status: IMPLEMENTED PROCEDURE — revised after the September 2026 rollback. Explicit audit/enforce mode, audit/bypass probe evidence, scoped verdicts, registry-selected per-loop state, audit-only assembly and owner enforce-readiness validation are implemented. The timestamp-reader sharing boundary is recorded in bite 5. Real authenticated host acceptance and live deployment remain separate owner acts; this document does not install a hook or change harness settings.

## Problem and measurement · `sec:permissiontriage:problem-and-measurement`

The harness's built-in classifier has generic safety knowledge but no installation-specific knowledge. A retained corpus contains 100 classifier interventions from two sessions: 86 Bash requests, 12 `ScheduleWakeup` requests, and two `Write` requests. Fifty-seven Bash requests were recorded as remote operations. Repeated denials include bounded worker checkout preparation, registered-server reads, timed gates, configuration reconciliation, privileged host changes, and credential-bearing changes; identical commands recur as many as four times, so an intervention teaches the default classifier nothing.

Applying the first-draft general rubric in this proposal to each retained row produces this mutually exclusive census. The corpus omits structured Bash timeout fields, so a timeout counts in this census only when the command text carries an explicit whole-command deadline; the implementation instead inspects the structured field before parsing the command.

|Class|Rows|Interpretation|
|-----|---:|--------------|
|`routine-general`|12|Ordinary harness lifecycle requests whose authority does not depend on an installation.|
|`routine-superloop`|0|This class requires an owner-rubric match, and the census deliberately uses the general rubric alone.|
|`safe`|2|Bounded project-document reads.|
|`advanced-read-only`|7|Read-only inspection outside the project or across a privilege or remote boundary.|
|`agent-error`|59|Mostly remote requests without a whole-command deadline, plus untimed builds and badly batched commands.|
|`suspicious`|20|Credential, permission, agent-configuration, host-security, destructive, transaction, or under-specified writes.|

Six suspicious rows are plausible owner-rubric candidates rather than intrinsically owner-only actions: two bounded lane dispatches, two registry-to-runtime mirror updates, one bounded disposable-lane cleanup, and one bounded remote lane preparation. Repetition means these six rows need fewer than six distinct owner rules. A corrected request rejected as `agent-error` may later become another owner-rubric candidate, but the defective corpus row itself does not earn installation-specific authority.

The objective is not to maximize allows. It is to replace repeated adjudication with a stable explanation: known generic work runs, explicitly taught installation work runs, malformed work returns to the issuing worker for repair, and uncertain work receives a scoped verdict for adjudication. In audit mode every verdict is evidence only; enforcement begins only after the acceptance and owner procedure in ``sec:permissiontriage:enforce-flip`` pass.

## Class ladder and decisions · `sec:permissiontriage:class-ladder-and-decisions`

The six-class vocabulary is fixed and serialized in this order. The permission column is the would-be decision recorded in either mode and emitted only in `enforce`. In `audit`, every row emits nothing on stdout and exits zero after journaling, leaving the harness gate to decide. A loop owner is the caller's loop orchestrator; an estate adjudicator receives only estate-scoped escalations. Scope is required for every verdict and is independent of classification: a bounded read of shared infrastructure can be `advanced-read-only` with `scope=estate` without becoming an escalation.

|Class|Enforce decision / audit would-be decision|Destination in enforce|Meaning|Generic example|
|-----|------------------------------------------|----------------------|-------|---------------|
|`routine-general`|`allow`|Requested tool|Ordinary bounded development or harness work needing no installation fact.|A correctly shaped `ScheduleWakeup`, or a timed project-local test.|
|`routine-superloop`|`allow`|Requested tool|A narrow owner-rule match or the registered role's domain grant, subject to all higher boundaries.|A timed gate on a registered worker alias inside its stated domain.|
|`safe`|`allow`|Requested tool|Low-risk local observation or contained project edit with explicit operands.|`sed -n '20,40p' docs/guide.md` in the current project.|
|`advanced-read-only`|`allow`|Requested tool|A bounded read across a remote, privilege, transcript, or configuration boundary that cannot mutate and is not expected to return secrets or private individual data.|A bounded read of a nonsensitive shared status file.|
|`agent-error`|`deny`|Issuing caller for correction|The request shape violates mechanical command hygiene.|A remote shell without a whole-command deadline, or an untimed build.|
|`suspicious`|`deny`|Loop or estate adjudicator according to scope|A destructive, security-sensitive, externally consequential, under-specified, or otherwise unapproved effect.|A worker's in-domain publication is loop-scoped; changing harness settings is estate-scoped.|

Audit journals the class, reason, scope, role, loop, stale-session flag, would-be decision, and measured wall for every path, including fast-lane allows, corrections, escalations, and infrastructure failures. Infrastructure failure is a separate status with no invented policy class and a would-be `deny`. Audit does not send a correction or escalation permission response and does not consume one-shot approvals. Its review stream must distinguish would-be denials from requests actually blocked by the harness.

The classifier reads every applicable rule and does not stop at the first candidate. Its conservative precedence is `suspicious`, `agent-error`, `advanced-read-only`, `safe`, `routine-superloop`, then `routine-general`; `suspicious` therefore beats every competing model classification. Deterministic fast-lane hygiene failures occur before model classification and return `agent-error` directly. An owner rule supplies the missing installation fact for `routine-superloop`; it does not suppress an independent suspicious property.

## Hook contract · `sec:permissiontriage:hook-contract`

The hook handles `PreToolUse`. The private instance file requires exactly one `PERMISSION_TRIAGE_MODE=audit` or `PERMISSION_TRIAGE_MODE=enforce`; an absent, duplicate, empty, unknown, or wrongly cased mode makes the instance malformed and fails closed. Neither `permission_mode` in request input nor an inherited environment value can supply a missing instance mode. The wrapper clears inherited deployment keys before parsing the closed instance grammar, and the binary validates the selected mode independently. Installation always registers a valid audit instance while retaining the existing harness permission mode; `bypassPermissions` is forbidden during audit. It parses `session_id`, `cwd`, `permission_mode`, `hook_event_name`, `tool_name`, `tool_input`, and `tool_use_id`; for Bash it additionally validates `tool_input.command`, `tool_input.description`, `tool_input.timeout`, and `tool_input.run_in_background`. Unknown fields are ignored for forward compatibility, but a missing required field makes the request unclassifiable and therefore produces a mode-dependent infrastructure would-be denial rather than a policy judgment.

The model receives only the tool name, current working directory, canonical command or action string, complete general rubric, complete optional owner rubric, resolved caller role, and complete optional domain rubric. Bash and `Monitor` use the exact command and the same shell-analysis path. Reviewed non-Bash actions carry only the reducer table's named scalar fields, counts, byte lengths, or ordered path list: prompt, message, write, edit, question, fetched, and artifact page bodies remain omitted. A reviewed MCP server becomes `mcp SERVER TOOL` plus only its allowlisted scalar string fields; an MCP server without an allowlist follows the unknown-tool rule. An unknown tool becomes `TOOLNAME fields=["SORTED","KEYS"]`, carries no values, and reaches the model as an ambiguous capability. If the adapter cannot form a reviewed reduction without losing a safety-relevant target, it produces an infrastructure would-be denial rather than sending the complete tool input; audit still emits nothing.

The nested invocation is one non-interactive process with the print, empty setting-sources, hook-disabling settings, strict-MCP, disabled-slash-command, configured-model, JSON-output, JSON-schema, no-tools, replacement-system-instruction, and no-session-persistence options pinned. The configurable `PERMISSION_TRIAGE_MODEL` default is `claude-opus-5`; it is not compiled as an unchangeable constant. Measurements on Claude Code 2.1.258 establish that empty setting sources and `disableAllHooks` suppress hooks, the two additional isolation flags are accepted, and stored OAuth remains available without bare isolation. The classifier runs from an empty private directory beneath the registry-selected loop state root (the estate diagnostic root for an unresolved caller) because auto-memory keys on the working directory and otherwise injects the current project's agent-written memory index; CLAUDE.md files were not observed in classifier context. An implementation test must pin the exact argument vector and structured-output envelope before parsing it.

Settings isolation is the default because a stored login is the common installation and bare isolation cannot read OAuth or keychain credentials. Bare remains selectable for installations that supply `ANTHROPIC_API_KEY` or an `apiKeyHelper` through settings. The hook never interpolates, logs, journals, or copies authentication variables into the model input. Missing or rejected authentication is a nonzero model failure and therefore produces an infrastructure would-be denial. Before installation, acceptance runs one authenticated classification through the deployed hook against the real classifier with the exact production argument vector, and one enforce classification with authentication deliberately unavailable that must produce the structured infrastructure-failure denial; both are recorded with their walls.

The revised model schema is an object with exactly three required fields and no additional properties: `classification`, whose enum is the six class names in their fixed order; `reason`, a non-empty string capped at 1,000 bytes; and `scope`, whose enum is `loop` or `estate`. Missing or unknown scope is a schema failure, never an implicit loop scope. The hook computes scope for deterministic and infrastructure results and validates model scope against the estate boundaries in ``sec:permissiontriage:escalation-journal``. The hook accepts exactly one structured object, rejects trailing data, validates the enum again after the CLI schema check, and treats an empty or oversized reason as unparseable.

In `enforce`, the hook emits one JSON object on standard output: `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"allow|deny","permissionDecisionReason":"…","additionalContext":"…"}}`. It never emits `ask`, so no person's desk is in this adjudication loop. An allow reason names the class and decisive rule; an `agent-error` denial begins `correction:` and names the smallest repair for the issuing worker; a `suspicious` denial begins `escalation:` and names the scope, caller role, loop, journal event, and responsible adjudicator; every degraded-path denial begins `infrastructure-failure:` and names the failed component while stating that no policy judgment was made. No reason repeats the command. `additionalContext` contains the same concise result for the calling agent. Normal serialized binary responses exit zero. No intentional path exits one or another unspecified nonzero status. The wrapper uses a structured infrastructure deny and exit two for an invalid instance or executable; the binary uses exit two when it cannot serialize or publish its response. The bypass probe must prove both exit-two forms block closed.

In a validated audit instance, the hook runs decoding, the nesting proof, role resolution, state selection, deterministic analysis, reduction, rubric loading, any required model call, scope validation, approval lookup without consumption, and journal publication before suppressing the permission response. A completed audit invocation writes zero stdout bytes and exits zero, including when its recorded would-be result is an infrastructure denial. This leaves the harness's existing authorization decision intact; it adds measured latency, not permission authority. If publication fails, a bounded stderr diagnostic identifies the lost audit event, emits no decision, and disqualifies the audit window; the design cannot claim a journal record survived a broken sink. A missing or malformed instance, an unavailable executable, a crash, or a harness-killed hook cannot complete this audit contract and fails the installation health gate. Missing or malformed mode always takes the structured fail-closed wrapper path, even if another line appeared to request audit.

The implemented nesting guard is `PERMISSION_TRIAGE_NESTED=PID:STARTTIME`, not a presence flag. The runner sets it only for its classifier child. The hook verifies the exact numeric shape, matching `/proc/PID/stat` start time, ancestry through the current parent chain, and the ancestor executable identity; a forged or stale proof is an infrastructure failure. A verified nested invocation skips policy recursion and returns the fixed nested allow in enforce. The revision journals a bounded nested diagnostic with mode, role, loop, scope, and wall and emits nothing in audit; it never starts a second classifier. The proof is not a general bypass available through command text. Acceptance deliberately exercises hook discovery with the isolation flags removed and proves both the valid and forged cases under bypass.

The named wall ceiling is `PERMISSION_TRIAGE_HOOK_CEILING_MS`, default 60000 and maximum 60000. The nested model deadline defaults to and is capped at 55000 milliseconds, reserving five seconds to terminate the child, validate or discard output, append the journal event, and emit the mode-appropriate response. At the model deadline the hook kills and reaps the child, records `model_timeout`, and produces an infrastructure would-be denial; enforce emits that denial, while validated audit remains silent. At the hook ceiling the harness terminates the hook; acceptance must prove that the harness blocks the request under `bypassPermissions`, and enforcement deployment is blocked if it does not. The registration uses the explicit 60-second timeout instead of the harness's 600-second default.

Model launch failure, nonzero model exit, timeout, output exceeding its cap, malformed JSON, schema mismatch, unknown classification, and journal failure all map to an infrastructure-failure would-be `deny`, emitted in enforce and journaled without a permission response in valid audit; none maps to `allow` or to `suspicious`. Malformed hook input maps to the same mode-dependent result, using null unavailable request fields; an enforce response that cannot be serialized uses exit two. The reason distinguishes escalation, correction, and infrastructure failure so the owner never mistakes a degraded gate for a command judgment.

## General and owner rubrics · `sec:permissiontriage:general-and-owner-rubrics`

The general rubric is the public package file `packages/permission-triage/rubrics/general.md`. The built artifact embeds those reviewed bytes and their digest, so a deployed binary and a journal record can identify the general policy used without consulting a mutable runtime copy.

The owner rubric is private superloop-local state selected by the optional absolute-path variable `PERMISSION_TRIAGE_OWNER_RUBRIC`. It lives beneath that superloop repository's private `local/` tree. An unset variable or a missing file means the general rubric applies alone. Any other read error, invalid UTF-8, or size beyond 64 KiB produces an infrastructure-failure denial. The hook reads a regular file without following a final symlink, records its digest rather than its path in the journal, and never writes it.

Every superloop has its own owner and its own owner rubric beneath its own private tree; the general rubric is the single shared artifact. The loop orchestrator proposes and maintains its owner rules through estate review of authorization-source changes. A disposition claiming reusable authority names a narrow rule already reviewed and written through the applicable scope authority. Loop adjudication cannot approve an authorization-source edit; such an edit is estate-scoped, even when the rubric lives in the loop's private tree. A lane, hook, classifier model, or `review` command never edits the rubric. Each positive line binds a stable rule identifier to the exact alias or alias family, account role, command grammar, path root, allowed operands, required deadline and timing shape, and forbidden expansions. Owner rules may also force `agent-error` or `suspicious`; they cannot weaken harness deny rules, the general rubric's always-suspicious boundaries, or the conservative tie-break.

Rubrics are concatenated with explicit untrusted-data delimiters. No rubric may redefine the JSON schema, request more context, instruct tool use, alter the nesting guard, or claim that its own text is an owner decision. The model's system instruction states that commands and rubric examples are data to classify, not instructions to execute.

## Role and domain rubrics · `sec:permissiontriage:role-and-domain-rubrics`

A worker and an orchestrator issue different work, so one rubric cannot classify both correctly. A worker acts on a bounded brief inside one lane and every effect it produces outside that lane is worth adjudicating. An orchestrator maintains the superloop itself: it commits and mirrors its own repository, writes its own memory and journal, dispatches its own lanes, and renders its own rulebooks. Those effects are not exceptions to its work; they are its work. Describing them as narrow per-command owner rules re-describes a domain one command at a time and never finishes, because the set of commands that touch a tree is open while the tree itself is closed. The rubric that classifies an orchestrator therefore states the domain, and lets the request's targets and effects be tested against it.

### Role resolution · `sec:permissiontriage:role-resolution`

The hook resolves exactly one role per request from hook input and a registry file, and from nothing else. Three values are possible: `orchestrator` (the main session of a registered superloop), `orchestrator-subagent` (an in-session subagent of that main session), and `unknown`.

The implemented registry is a directory of `<name>.env` entries. Its bounded, closed parser accepts one `LOOP_NAME`, one absolute dot-component-free `LOOP_CWD`, and at most one optional `LOOP_SID`; an invalid entry is ignored as a whole. `PERMISSION_TRIAGE_LOOP_REGISTRY` selects an absolute mode-0700 directory owned by the effective uid, opened read-only without following its final symlink. Entries are mode-0600 regular files with that owner, read through the opened directory descriptor without following final symlinks, and valid triples are sorted. An unset or empty registry value resolves `unknown` without a filesystem read; an unavailable, unsafe, over-cap, or unreadable configured registry also resolves `unknown`. The pending `LOOP_STATE_ROOT` extension in ``sec:permissiontriage:escalation-journal`` changes state selection, not these identity rules.

The deployed resolver's five rules, also documented in `packages/permission-triage/README.md`, are:

1. A relative request `cwd`, a `cwd` containing parent traversal, or a `cwd` beneath no registered checkout resolves `unknown`.
2. The candidate is the entry whose `LOOP_CWD` equals or is an ancestor of the normalized request `cwd`. The longest checkout wins only when all matches are strictly nested; duplicate or otherwise ambiguous checkout matches resolve `unknown`.
3. A request `session_id` that matches a different entry's `LOOP_SID` than the checkout-selected candidate makes the role `unknown`.
4. A candidate with a registered `LOOP_SID` resolves only when the request `session_id` matches it; a mismatch resolves `unknown`. A candidate without `LOOP_SID` resolves by checkout alone. Every resolved role records `stale_session=false`.
5. Once the candidate passes those checks, a truthy `agent_id` or a `transcript_path` containing `/subagents/` selects `orchestrator-subagent`; otherwise it selects `orchestrator`.

The checkout is the primary key and `LOOP_SID` is optional corroboration. A matching session identifier cannot rescue an outside-checkout cwd, and a rotated session identifier alone cannot remove a valid checkout grant. Scratchpad and lane paths named as domain targets do not automatically become caller identity roots: requests must originate beneath a registered checkout or an explicitly provisioned registry checkout. The optional `agent_id` and `transcript_path` fields reuse the SessionStart audience signal; absent or wrongly typed optional values do not fail decoding and, without a subagent signal, a valid candidate resolves as `orchestrator`, not `unknown`.

Environment values are not evidence about a request. `CLAUDE_CODE_CHILD_SESSION`, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_ENTRYPOINT`, and `CLAUDE_PID` are inherited through a process chain rather than delivered with the request, they are not bound to the `tool_use_id` being decided, and a shell request can place names into the environment of processes it starts. The orchestrator hook already derives its whole audience decision from hook input and reads the environment only for `HOME` and for its own configuration; the triage hook holds the same line. The role is derived from hook input plus a reviewed registry file, and it reaches the model as data in a length-delimited section, never as an environment value and never as an assertion the model is asked to trust about itself.

### What a domain rubric is · `sec:permissiontriage:domain-rubric`

A **domain rubric** is one file per loop, private, beneath that loop's `local/` tree, at `LOOP_CWD/local/permissions/domain.md`. It is loaded by the same secure loader the owner rubric uses: absolute path, final component opened read-only without following a symbolic link, regular file, at most 64 KiB, valid UTF-8, digest computed over the exact bytes read. An absent file means no domain grant in the current loader; it is a failed precondition for revised installation and enforcement readiness. Any other read failure is an infrastructure would-be denial, as for the owner rubric. The digest is recorded in every journal record and in the deployment record, so a decision can be traced to the exact domain text that produced it, and the configured path is never exposed to the model.

Its content is a statement of facts, not of permissions: the loop's checkout and private tree; its scratchpad root and lane-clone root; its auto-memory directory; its registered remotes with the ssh aliases and key-only server accounts that reach them; its server-side loop root; its lane runtime paths and run directories; its escalation journal and state root; its rulebook render targets. Its single grant clause follows from those facts: a request whose targets and effects lie wholly inside the stated domain is `routine-superloop`. The grant is subject, without exception, to the general rubric's always-suspicious boundaries and to every hygiene rule, so a badly shaped in-domain request is still `agent-error` and an in-domain request that touches credentials, harness settings, hooks, host or network configuration, or untrusted code is still `suspicious`.

A domain rubric may not name another loop's paths, remotes, accounts, or aliases; may not redefine the output schema, the class ladder, the deadlines, the journal requirement, or the nesting guard; and may not claim that its own text is an adjudication. Those constraints are the owner rubric's constraints, unchanged, because a domain rubric is the same kind of artifact: reviewed private data whose author is the loop that bears the consequences.

### What the owner rubric is still for · `sec:permissiontriage:owner-rubric-role`

The owner rubric keeps the job it can do that a domain rubric cannot: narrow grants that deliberately cross the domain edge. Rendering the routine rulebook map writes into the harness root's `~/.claude` tree, which is outside every domain and always will be. One loop provisioning another loop's server account touches a second loop's facts by definition. A bounded read of a shared estate path belongs to no single domain. Each needs a scope-specific decision with named operands; an authorization-source write or another loop's account change remains an estate escalation rather than earning an allow from a loop-authored rule. For eligible bounded reads, enumerating operands per command is the right shape — the objection to per-command rules was never that they are wrong, only that they cannot describe an open set. Owner rules also keep their negative direction: a rule may force `agent-error` or `suspicious`, and no rule of any kind may weaken a harness deny rule, an always-suspicious boundary, or the conservative tie-break.

### Subagents · `sec:permissiontriage:subagent-domain`

A subagent of a registered orchestrator receives the same domain and a **narrower** grant: reads and in-domain edits are `routine-superloop`, while four effect classes stay `suspicious` even inside the domain — publication to the loop's hubs, writes to the auto-memory directory, lane dispatch, and any operation using the loop's server account.

The reason is a difference in what the two contexts ingest. The orchestrator's main session is where the loop's supervision lives: its turns are composed against the loop's own record and a person can read that transcript. A subagent runs on a prompt the orchestrator composed but then ingests file contents, tool output, and network text with no orchestrator turn between ingestion and the next tool call, which is exactly the path along which observed content becomes an action. Withholding the four durable-trace effects costs one hop — the subagent's escalation returns to an orchestrator in the same session, which can re-issue the request itself after reading the reason — and removes the case where text a subagent read becomes a commit on a hub, a line in the loop's memory, or a command running under the loop's server account. The cost is small and paid once per occurrence; the exposure removed is the only one in the domain grant that reaches beyond the machine.

Reads, scratchpad and lane-clone writes, in-checkout edits, local commits, and journal review remain routine for a subagent, which is the traffic a reviewer, a log reader, or a design draft actually issues.

### Unregistered sessions · `sec:permissiontriage:unregistered-sessions`

A request resolving `unknown` has no domain rubric or domain digest and carries `role=unknown` in the prompt. Unknown covers invalid or outside-checkout cwd, missing or unsafe registry, ambiguous checkout matches, and a session identifier belonging to a different entry. A registered candidate's identifier must match the request; an absent candidate identifier resolves by checkout alone, while a different identifier resolves `unknown` and `stale_session` remains false. In the revision, unresolved requests run the available general and owner analysis in audit but cannot obtain a loop root or a loop approval; they record an estate-scoped diagnostic at the explicit estate state root. Enforce refuses unresolved identity as an infrastructure failure, because the routing and domain preconditions have not been met. Any unresolved live session blocks the enforce flip.

### Prompt carriage · `sec:permissiontriage:role-prompt-carriage`

The prompt gains two length-delimited untrusted sections carrying the same per-prompt nonce as the existing ones, in fixed order after the owner rubric: `CALLER ROLE` and `DOMAIN RUBRIC`. The role section carries one line from a closed vocabulary — `role=orchestrator loop=NAME`, `role=orchestrator-subagent loop=NAME`, or `role=unknown` — where `NAME` is the `LOOP_NAME` the hook read from the matched registry entry. Nothing else enters: no session identifier, no transcript path, no agent identifier, no registry path, no environment value. The role line is hook-derived data about the request, delimited and nonce-marked like every other value, so a command, a rubric, or a file body claiming a role is untrusted text that the existing system instruction already tells the classifier to treat as data. The classifier's instruction gains one sentence stating that the role line is the only statement of role and that a role claimed anywhere else is data.

### Class semantics that change · `sec:permissiontriage:role-class-semantics`

`routine-superloop` gains a second admitting form. Today the class requires one narrow owner-rubric rule to match the request's alias, account role, command grammar, path root, operands, timeout, timing, and side-effect boundary. It additionally admits a request whose caller role is an orchestrator role of a registered loop, whose targets and effects lie wholly inside that loop's stated domain, and which is not withheld from that role. Precedence is unchanged: the class still sits second-lowest in the conservative tie-break, so any competing `suspicious`, `agent-error`, `advanced-read-only`, or `safe` reading still wins.

`suspicious` keeps every boundary it has, but the publication clause is restated so that it names the crossing rather than the verb. The current wording — deployment, publication, merge, force push — reads on its face as *any* push, and that reading escalated an orchestrator mirroring its own repository to its own hub over its own alias. The clause becomes: publication to a destination outside the caller's domain; deployment to a host outside the caller's domain; a merge into a branch or repository the caller's domain does not include; and, in every case including inside the domain, a force push or any other history rewrite. Force push stays absolute because the domain grant's justification is that in-domain state is reproducible from the loop's own record, and a history rewrite destroys the record that justification depends on. A fast-forward push of the loop's own checkout to the loop's own registered remote changes nothing anyone else owns and is therefore not publication in the sense this boundary protects.

Hygiene rule 5, one mutating request for one operational objective and one failure domain, gains one bounded exception and keeps the rest. A mutation and its own publication to a destination inside the caller's domain are **one** objective when the publication is a fast-forward of exactly the mutation just made: the test the rule enforces is whether a partial failure leaves a state the request cannot attribute, and here it does not — a failed push leaves the commit intact and locally identified, and the repair is a rerun of the push alone with nothing to disentangle. A commit followed by a force, by a push to a different remote, by a non-fast-forward, or by any third action keeps the multi-objective correction. The chained `git add && git commit && git log` the deterministic lane corrected is unaffected and stays corrected: staging and committing are one objective, but appending a verification read to a mutating batch is precisely what the rule splits, so the failing action and the permission decision stay attributable. The domain grant does not make a badly shaped request well shaped.

### Trust argument · `sec:permissiontriage:domain-trust-argument`

The domain grant is safe because of what it is bounded by, not because of what it trusts. A domain contains only state the loop already owns, already writes as a matter of routine, and can reproduce from its own records; the party who bears a mistake inside it is the party who made it. The grant adds no capability a loop did not already have by construction — the gate's purpose is to stop effects crossing outward, not to police a loop's use of its own tree — and it moves no boundary: credentials and private keys, harness settings and hooks and instruction files, other loops' checkouts and hubs and journals and accounts, host and network configuration, untrusted code execution, endpoint literals where aliases are required, and materially ambiguous targets are all outside every domain and stay `suspicious`.

Role resolution relies on harness-supplied cwd and optional session corroboration, not cryptographic caller identity. Longest strictly nested checkout selection and rejection of another entry's session identifier prevent known disagreements from acquiring a domain grant; stale-session journaling exposes identifier rotation without discarding the checkout. Those checks do not prove that a compromised harness or falsified cwd cannot select another loop, so the design does not claim that a wrong role can never reach that loop's tree. Registry integrity, trusted hook input, domain containment, and complete audit coverage are explicit premises. Every decision records role, loop, stale-session flag, and all rubric digests so the premises can be checked before enforcement and regressions investigated afterwards.

The grant does not cover the loop's ability to change what its domain is. The domain rubric is reviewed private data, it is read no-follow with a digest recorded on every decision, and a request that edits a domain rubric is a change to an authorization source and is `suspicious` with `scope=estate` under the existing agent-configuration boundary, exactly like a request that edits an owner rubric. The loop registry is the same kind of surface one level up: it is what decides which role a request resolves to at all, so it stays outside every domain with the rubrics, and a request that writes a registry entry is `suspicious` with `scope=estate` for the same reason — a role a loop can hand itself is not a role.

### Adjudication authority · `sec:permissiontriage:adjudication-authority`

Adjudication follows effect scope. A worker, including a Codex lane or an in-session subagent, reports a loop-scoped suspicious event to its own loop's main session; that session adjudicates in the loop journal. A loop orchestrator's own loop-scoped suspicious request goes to the same journal for its owner to review. Only estate-scoped requests go to the estate orchestrator and estate journal. The role field still uses the three implemented role values; “worker” describes the reporting relationship and does not invent an unsupported fourth role.

Loop review may reject a request, record an already approved narrow rule, or mark a prior loop escalation `adjudicated-approved`. The one-shot approval binds the original event, request digest, scope, caller loop, caller role, and authorization digests, and is consumed under the journal lock with the resulting enforce decision. It never grants a different request, another loop, a subagent retry, or an estate-scoped action. A worker's approved work is re-issued by its loop orchestrator, producing its own request record; the worker cannot consume an orchestrator-role approval. Audit may record that an eligible approval would match but neither consumes it nor emits an allow. Concurrent identical retries must yield at most one consumption.

Estate review uses the estate journal and explicit estate adjudication authority; ownership of a loop journal supplies none. Harness settings and hooks, instruction and authorization sources including owner/domain rubrics and the registry, host/network configuration, shared hubs, server-account provisioning, toolchains, the gateway, and another loop's state are estate-scoped. A loop's use of its own provisioned hub or server account for domain work is not a modification of the shared hub service or account configuration. A loop may submit proposed rubric text, but neither a loop approval nor a rubric rule can weaken an always-suspicious boundary or install that authorization change. Estate maintenance of those surfaces is a separately authorized operation, not an automatic allow minted by a journal mark.

Review and ordinary loop disposition records are bounded domain work; approval creation still verifies adjudicator identity and scope, and a worker cannot mark its own approval. The one-shot mechanism makes loop-scope exceptions deliberate and attributable, but cannot contain a fully compromised loop orchestrator within its own domain. Estate boundaries and infrastructure failures remain enforced independently of loop approvals.

## Deterministic fast lane · `sec:permissiontriage:deterministic-fast-lane`

The fast lane is deliberately closed and ordered. It either returns a table-owned read-only allow or a mechanical `agent-error`; every other request reaches the classifier model. A shell parser, not substring matching, determines command structure, and any parse ambiguity leaves the fast lane.

The installed CLI exposes a semantic `Read-Only Operations` allowance but no machine-readable exact command roster, and it enforces no read-only boundary of its own that this design could borrow: given no settings rule to decide the request, no negative twin was refused. Of 66 negative trials, 61 executed with a `PreToolUse` followed by a `PostToolUse` and no denial, among them a `Read` outside the project, Bash forms redirecting their output outside the project, and a web search carrying a sentinel token; three GET-`WebFetch` negatives recorded a lone `PreToolUse` and no outcome event at all; and two `readlink` negatives were truncated at the invocation ceiling. The read-only authority is therefore the hook's own version-pinned table, which admits a request only when it matches an entry's exact grammar and that entry is accepted, and which routes everything else to the classifier model. The acceptance matrix no longer discovers a harness boundary. Its role is to confirm, under the deployed topology and with the real hook installed, what the hook mechanically does with each member: the positive form is admitted by the table and decided without a model call, and the negative twin is not admitted by the table and reaches the model. Both halves are observable because the matrix drives the hook with the fixture's fake model CLI, exactly as the real-hook matrix does, so the model answer is deterministic and its invocation leaves a capture the trial can test. A positive trial passes when the hook response reason begins with the table's read-only prefix, `safe: harness read-only rule` followed by the entry name, and no fake-model capture exists. A negative trial passes when that capture exists, whatever verdict the fake model is configured to return, since reaching the model is the whole claim. The capture rather than the reason is the decisive negative observation, because the model's own `safe:` allow and the table's `safe:` allow share a prefix; the other model-path reasons begin `routine-general:`, `routine-superloop:`, `advanced-read-only:`, `correction:`, or `escalation:`. AUTO/manual comparisons remain characterization evidence. In the target enforce topology the harness classifier is bypassed, so the table and triage classifier carry the entire permission judgment; in audit the same table result is journaled and the existing harness gate still decides. No table entry is justified by an assumed second classifier. Each item below names its table entry, the grammar that entry admits, and the twin that must leave the table; no entry is accepted until the matrix passes for it and this proposal is revised.

1. Entry `native-read` admits a `Read` whose `file_path` is a project-relative, nonsensitive regular file with optional nonnegative `offset` and `limit`, because that decided grammar carries no write channel. Its twin is a `Read` of an outside-project or sensitive path, which matches no entry and leaves the fast lane.
2. Entry `native-glob` admits a `Glob` with a nonempty pattern and an optional project-relative path, neither escaping the project, because enumeration returns names and mutates nothing. Its twin is an enumeration rooted outside the project.
3. Entry `native-grep` admits a `Grep` with a nonempty pattern and an optional project-relative, nonsensitive path, because content search has no mutation primitive. Its twin is a search rooted outside the project or aimed at a secret-bearing target.
4. Entry `native-web-search` admits a `WebSearch` whose nonempty query carries no credential-shaped value, because the request mutates nothing locally while the query itself leaves the machine. That exclusion is the hook's alone: the harness runs a sentinel-bearing query without objection, so nothing but the table keeps a credential out of a search. Its twin is exactly such a query.
5. Entry `native-get-web-fetch` admits a `WebFetch` with an HTTP(S) URL, an absent or GET method, no body or upload field, and no credential-shaped URL. Because the WebFetch tool input has no method or body field, its executable positive is a GET of `https://example.com/` and its excluded twin is a GET of the credential-shaped URL `https://triage:TRIAGE_NEGATIVE_SENTINEL@example.com/`, whose authority contains `@`. The earlier run's identical `PreToolUse`-only lifecycles came from a non-resolving host rather than from a harness property. Lifecycle events alone still cannot arbitrate the table: with the entry disabled, both a matching positive and an excluded negative route to the model, so the deterministic capture is what distinguishes table admission. A negative twin's tool outcome is never graded, because the capture alone proves the row did not admit it; that is what lets this credential-shaped twin serve even though the tool rejects it before any request.
6. Entry `bash-filesystem-observation` admits one simple `pwd`, `ls`, `stat`, `file`, `readlink`, or `wc` command carrying only encoded observation options and project-relative operands; redirects, command substitution, `find`, and any outside-project operand are excluded. Its twin is such a command reaching an operand outside the project.
7. Entry `bash-source-observation` admits one simple `rg`, `grep`, `sed -n`, `head`, `tail`, or read-only `jq` command with encoded options and project-relative file operands; in-place flags, output-file flags, executable expressions, redirects, substitutions, and outside-project operands are excluded. Its twin is the in-place form of the same tool.
8. Entry `bash-repository-observation` admits one simple `git status`, `git diff`, `git log`, `git show`, or `git rev-parse` command without relocation, remote contact, or mutation. Its twin is a subcommand that contacts a remote or updates an index, a worktree, or an object.

Mechanical defects return `agent-error` without spending a model call:

1. `ssh`, `scp`, `sftp`, `rsync` over a remote shell, and equivalent remote execution or transfer require a finite positive `tool_input.timeout` that bounds the whole Bash request; a transport connection timeout alone does not bound an established command.
2. A background or detached request requires `run_in_background=true`, a finite startup timeout, a stable job identity, an append-only log, and a completion marker or supervised status command; otherwise the caller has supplied no bounded observation contract.
3. Every build, test, linter, package installation, image build, and other potentially long gate is wrapped at its execution boundary by `time` or an accepted wrapper that emits elapsed wall time and child status; timing only a later pipeline consumer is insufficient.
4. A mutating batch may have only one operational objective and one failure domain. Independent host changes, source-control publication, configuration writes, and verification runs are separate requests so the failing action and permission decision remain attributable.
5. A mutating or gate command may not pipe into `head`, `tail`, `grep`, or another consumer unless pipeline failure propagation and the producer's exit status are preserved explicitly; attractive output is not evidence of success.
6. A destructive operand may not depend on an unresolved environment variable, wildcard, command substitution, empty string, current-directory assumption, parent traversal, or broad root. The request must name a validated, bounded target.
7. A remote privileged command must be non-interactive, must use the configured alias rather than an endpoint, and must not depend on a password or host-key question; otherwise it can hang or cross an undeclared destination.
8. Pseudocode, prose placeholders such as an unevaluated parenthetical, unclosed quotes, malformed heredocs, and shell text that cannot be parsed as the declared action are wrong-shaped requests rather than policy questions.

## Escalation journal · `sec:permissiontriage:escalation-journal`

The revised registry entry adds exactly one required `LOOP_STATE_ROOT` for each deployable loop. It is an absolute dot-component-free path provisioned at its registered location, which may lie outside the checkout and is separate from authorization files, every registered `LOOP_HOME`, and every other loop's root. The hook selects it from the same validated registry snapshot and checkout-selected entry that produced the role; it never constructs a root from untrusted request fields or accepts a caller-supplied root. The directory is mode 0700, owned by the effective uid and opened without following symlinks; the journal is a mode-0600 regular file accessed through that directory descriptor. Duplicate, nested, shared, symlinked, or unsafe roots fail deployment validation; an unavailable selected root is an infrastructure failure. The registry parser extension must not turn optional `LOOP_SID` into a requirement or alter the five identity rules in ``sec:permissiontriage:role-resolution``.

`PERMISSION_TRIAGE_STATE_ROOT` remains an explicit instance path only for selecting the estate journal and unresolved-identity diagnostics; it is no longer a fallback journal for resolved loops. It must equal the registered estate loop's `LOOP_STATE_ROOT` and pass the same checks. That root has two distinct streams: `escalations.jsonl` for the estate orchestrator's own loop-scoped work and `estate-escalations.jsonl` for estate-scoped work from any caller. Scope selects the filename through a closed mapping, with independent corresponding lock files; it never comes from a request path. A valid audit instance with an unavailable registry can still record an estate-scoped unknown-role diagnostic there; that evidence blocks enforcement. Failure of a known loop's sink does not copy its loop-scoped record into the estate journal. It produces a bounded degraded-audit stderr diagnostic in audit or an infrastructure denial in enforce. This preserves the invariant that only estate-scoped records reach the estate journal, including estate-scoped infrastructure diagnostics for callers with no resolved loop.

Scope is required for every classification, fast-lane result, diagnostic, disposition, and approval-consumption event. `loop` means targets and effects belong wholly to the caller's registered domain and touch no estate boundary. `estate` includes harness settings and hooks; instruction or authorization sources such as rubrics, registry entries, and approval-authority configuration; host or network configuration; shared infrastructure configuration or operation outside a loop's provisioned domain, including hubs, server accounts, toolchains, and the gateway; and another loop's state. Unknown identity or an unresolvable effect scope is `estate`. The classifier returns the scope with its class; deterministic paths compute both, and known protected targets impose an estate scope floor which model output and approvals cannot lower. A claimed loop scope contradicting a protected target is a schema/validation infrastructure failure, not a silent reroute that might preserve an unsafe allow. Uncertain operations leave the fast lane and the model's ambiguity rule selects `suspicious` with `scope=estate`.

Each loop root contains `escalations.jsonl` and an empty private `classifier-cwd`; the estate root additionally contains `estate-escalations.jsonl`. Despite their historical escalation names, these journals contain every verdict of their respective scope, not only suspicious results. Append uses one locked write followed by data synchronization, capped at 8 KiB per record. Schema 2 classification records contain `schema`, `event`, `event_id`, `recorded_at`, `tool_use_id`, `request_digest`, `tool`, `cwd`, `command`, `classification`, `reason`, `scope`, `mode`, `would_be_decision`, `emitted_decision`, `role`, `loop_name`, `stale_session`, `general_rubric_digest`, `owner_rubric_digest`, `domain_rubric_digest`, `model_status`, `wall_ms`, and `model_wall_ms`. `classification` is one of the six names or null for infrastructure/guard diagnostics; unavailable identity/request/digest fields are null, `role` is `unknown` when unresolved, and `stale_session` is false when no loop resolved. `would_be_decision` is `allow` or `deny`; `emitted_decision` is null in audit and the intended serialized decision in enforce, not proof that the tool executed. `wall_ms` is a nonnegative monotonic elapsed integer from hook entry through verdict preparation immediately before append; `model_wall_ms` is null without a model call. Probe invocation wall additionally measures append, synchronization, and response/exit, so the friction budget cannot hide journal latency.

Disposition events retain source correlation and add `outcome`, adjudicator loop/role, and source scope. Outcomes are `escalated`, `adjudicated-rule-added`, `adjudicated-rejected`, `corrected-and-rerun`, and `adjudicated-approved`; `approval-consumed` remains a separate correlated event. Audit suspicious records retain the escalation relationship but their mode and null emitted decision prevent review from describing them as hook-blocked requests. Schema 1 history remains readable for review, explicitly labeled legacy/unscoped and excluded from audit acceptance and approval consumption; no migration guesses its scope or rewrites old evidence.

Loop-scoped records are appended only to the caller's registry-selected `escalations.jsonl`, including when that caller is the estate orchestrator. Estate-scoped records, preserving caller loop/role, are appended only to the estate root's distinct `estate-escalations.jsonl`; the caller's reason or audit report carries the event ID and destination, without duplicating command text into a second journal. A worker reports a loop escalation to its own main session, which adjudicates there; a main-session loop escalation waits there for its owner. An estate escalation reaches the estate orchestrator through the report naming its estate event. `agent-error` is a correction for the issuing caller, even when its evidence scope is estate, and infrastructure failures are health diagnostics, not policy escalations. No lifecycle event or free-text result implies that a denied or audit-observed request ran.

The read-only review command selects journals by registered loop identity and scope, groups by scope, caller loop, role, and normalized request shape, and renders candidate rules without writing authorization. Mark forms require a prior event in that same journal and scope, reject worker self-approval and cross-loop marks, and never consume a legacy approval. Loop owners review their own loop journals; the estate orchestrator reviews the estate-scoped journal. Private modes, capped command retention, bounded reason rendering, and omission of tool output, session identifiers, transcript paths, and rubric bodies remain mandatory. This layout isolates routing, not operating-system principals: loops sharing a uid still depend on the hook and registry as authorization boundaries.

## Security argument · `sec:permissiontriage:security-argument`

In the target topology no generic AUTO classifier supplies a second permission judgment. The hook must run on every gated tool request under `bypassPermissions`, its deny must prevent execution, and its allow must be final subject to the separately measured settings deny rule. These are empirical premises proved by ``sec:permissiontriage:topology-acceptance`` on the exact supported harness version, including settings-deny ordering; the design does not infer them from a mode name or from historical manual/AUTO behavior. If a missing executable, hook crash, exit two, timeout, malformed instance, classifier failure, or failed journal can fall through to execution, sole-gate enforcement is unsafe and cannot be activated.

A successful enforce allow therefore requires a valid instance, trusted hook invocation or narrowly proven nested child, resolved registered identity, safe selected state, a valid deterministic/model result, scope validation, all higher policy boundaries, and durable journal publication. A loop approval cannot skip infrastructure checks or estate boundaries. Class precedence is conservative and an independent suspicious property wins over domain/owner grants. Model misclassification remains a residual risk: fail-closed infrastructure and audit evidence do not prove that a model always recognizes malicious intent. Replacing the harness classifier is justified only by the measured corpus, boundary twins, and live audit acceptance, with regression checks on any model, rubric, registry, or harness change.

The classifier has no tools, session persistence, hook discovery, project instructions, or prior tool output. It receives the reduced action, cwd, tool name, general/owner/domain rubrics, and resolved role only. Reviewed reducer scalars may include the Agent/Task caller-authored description; file bodies, transcripts, session identifiers, journal contents, and authentication variables remain excluded. A secret already in command text can reach the model because removing it could alter the action; no additional secret source is supplied. The PID/start-time/ancestry/executable nesting proof confines its exception to the isolated child and must pass forged-proof tests in bypass mode.

Audit removes the hook's decision output only after a valid audit mode is established, preserving the active harness gate while measuring every would-be verdict. It does not promise zero latency or surviving evidence from a broken disk. Complete role coverage, acceptable wall distributions and model-call share, reviewed would-be-denial share, zero peer-domain denials, and zero evidence gaps are prerequisites for the explicit enforce flip. The transition order in ``sec:permissiontriage:enforce-flip`` prevents an audit-plus-bypass interval with no permission gate.

Per-loop roots and scope-bound review prevent one loop's routine supervision from arriving in another loop's journal or acquiring estate authority. Only estate-scoped records reach the estate journal. Registry, rubric, and approval-authority configuration edits remain estate-sensitive even beneath a loop's private path. Sharing an effective uid provides no filesystem isolation between loops, and harness input is not a cryptographic identity proof; those trust limits are explicit. Private append-only evidence, source-correlated approval consumption, and review tools with no rubric write path make exceptions auditable without granting workers or the classifier the ability to approve themselves.

## Deployment under private loop homes · `sec:permissiontriage:deployment-under-private-loop-homes`

Every deployment path above was written for an estate in which a loop's checkout was a directory of the session's own uid, so that one path could name the loop's identity, its reviewed authorization data, and its private evidence at once. That premise is gone. Each loop's clone now lives in a private home owned by a subordinate uid and is entered only through a command that switches to that uid, while the session that raises permission requests still runs at the owner's uid with its working directory set to a launch directory that holds none of the loop's material. The hook runs at the session uid. Every path the current contract derives from `LOOP_CWD` — the domain rubric at `LOOP_CWD/local/permissions/domain.md`, the owner rubric and state root required to lie beneath `LOOP_CWD/local/` — is therefore either absent or unreadable to the process that must read it, and the layered ownership checks that made those paths safe can no longer pass for anything inside a loop home.

Two answers to that loss are available, and they differ in which side moves. The first moves the files toward the reader: every artifact the hook must open leaves the loop homes for trees at the deployment uid, and the hook opens them where it already stands. It works, and its cost is that once every loop's authorization data and evidence sit at one uid, nothing but a path prefix separates one loop's from a peer's — so the boundary between loops becomes a rule something must police on every deployment, over a tree in which a mistaken prefix looks exactly like a correct one. The second answer moves the reader toward the files: each artifact stays with the principal responsible for it, and the process that reads it runs as a uid entitled to read it. That is the design this section writes.

The argument for it is that the two answers put the same boundary in different enforcers. A prefix rule is enforced by whatever reads it — the assembler at deployment, the validator at run time, a person reading a registry — and holds only while all three agree about what the prefix means. A uid is enforced by the kernel on every open, for every process, including the ones nobody had in mind when the rule was written: a Codex driver, a shell a worker starts, a tool that follows a symbolic link. This document's own trust argument already concedes the difference by listing registry integrity and domain containment as premises rather than as guarantees, and ``sec:permissiontriage:escalation-journal`` states plainly that the layout isolates routing rather than operating-system principals. The estate has since acquired operating-system principals. Using them removes premises instead of adding them.

Three tiers follow, each owned by the uid responsible for what it holds: an estate tree at the orchestration loop's uid, one home per loop at that loop's uid, and one tree per worker at a uid of that worker's own. This section states the tiers, places each artifact in one of them, derives identity and adjudication from the placement, and lists the migration and the code it needs. The launcher the third tier requires is proposed separately in [the worker launcher](run-worker.md); this section states only what the gate needs from it.

### Measured starting state · `sec:permissiontriage:private-home-measured-state`

The following were measured on the deployment host on 2026-09-22 and are the facts the rest of this section argues from.

- The estate loop's clone is `LOOP_HOME/orchestration`. The home is mode 0700 and owned by a subordinate uid that the session's uid namespace renders as `nobody`, so the ownership comparison in `verify_directory_mode` and `open_state_root` can never succeed for a path inside it. One peer loop has the same shape at its own subordinate uid; two further registered loops have not been moved.
- The session's request `cwd` is its registered launch directory beneath `$HOME/dev/`, which holds `CLAUDE.md` and the harness's own `.claude/` project directory and nothing else. All of the loop's material is reached through `enter-loop <loop> -- <command>` from the estate's public superloop tooling checkout.
- The registry directory is mode 0700 and owned by the session uid, which is exactly what `load_registry` requires. Entries carry `LOOP_NAME`, `LOOP_SID`, and a `LOOP_CWD` naming the launch directory; the two moved loops additionally carry `LOOP_UID` and `LOOP_HOME`. No entry carries `LOOP_STATE_ROOT`.
- One registry entry is mode 0644. `read_registry_entry` requires mode 0600 and its failure propagates out of the directory scan, so one non-conforming entry makes the entire registry unreadable and resolves every request `unknown`.
- `parse_entry` returns `None` for any key outside its closed set and an unparsed entry is dropped whole, so `LOOP_UID` and `LOOP_HOME` drop the two moved loops' entries even once the mode is repaired.
- The live instance `$HOME/.claude/permission-triage.env` carries no `PERMISSION_TRIAGE_MODE`, which the wrapper rejects as malformed, and names a state root and owner rubric beneath `LOOP_CWD/local/permissions/`, a directory that does not exist because the launch directory has no `local/` tree.
- The wrapper, hook binary, review binary, and topology binary are installed under `$HOME/.claude/hooks/` at the session uid, so the adjudication command already runs where the journal must be readable.
- `rubrics/general.md` is embedded by `include_str!` together with its digest, so the general rubric needs no filesystem location and no placement decision; a deployment cannot repoint it without replacing the binary, which is the property that makes it the single shared artifact.
- Lane clones live at `$HOME/.cache/tmp/lane-<name>`, beneath no registered checkout, and therefore resolve `unknown` under rule 1 of ``sec:permissiontriage:role-resolution``.
- Measured on the deployment host on 2026-09-23 (a `PreToolUse` capture hook on a lane session that ran one Bash call, one foreground `general-purpose` subagent making one Bash call, and one more Bash call): the subagent's hook input carries `session_id` equal to its main session's, `transcript_path` naming the main session's own transcript rather than a file under `subagents/`, and non-null `agent_id` and `agent_type` (`general-purpose`), while the main session's own calls carry null `agent_id` and `agent_type`. Two consequences for the identity rules: requiring an exact `LOOP_SID` match cannot resolve an in-session subagent `unknown`, because it presents the registered identifier; and of the two subagent signals rule 5 of ``sec:permissiontriage:role-resolution`` accepts, only a truthy `agent_id` fires on this harness, since the transcript path carries no `subagents/` component. The bite that requires the identifier therefore lands as stated, with the fixture recording these three inputs verbatim.

Three of these are defects rather than design questions: the entry mode, the missing instance mode, and the two unparsed registry keys. They are repaired by the migration below whichever design is chosen, and until they are repaired no measurement of this gate on this host means anything, because the registry load fails before identity is attempted.

### Three tiers of ownership · `sec:permissiontriage:uid-tiers`

An artifact belongs to the tier of the principal that may write it, and is readable at the widest boundary its content permits. That rule produces three tiers and assigns every artifact this gate uses to exactly one of them.

|Tier|Owned by|Written by|Readable by|Holds|
|----|--------|----------|-----------|-----|
|Estate|the orchestration loop's subordinate uid|that loop, through its entry command|every uid|The loop registry, the general rubric's source and the owner rubric, one orchestrator rubric per loop, the deployed hook binaries and the instance file, one journal directory per loop, and one estate outbox per loop.|
|Loop|the loop's own subordinate uid|the loop, through its entry command|`private/` the loop alone; `shared/` the loop's group; `workers/LANE/` that one lane; `runs/` every uid|The clone, memory and keys; the worker rubric and the shared logins; one worker tree and one run directory per lane.|
|Worker|a uid allocated to that lane alone, in the loop's group|that worker|its loop, and every uid for the run directory|The lane clone, the worker home, and everything the run produces.|

The worker's credentials are a value this design must state rather than inherit, because every group-mediated row above depends on them and the entry command's drop supplies none of them. That drop is `setpriv --reuid=UID --regid=UID --clear-groups` with one uid for both fields (`packages/loop-home/src/planner.rs:110-112`), and the passwd and group lines it appends name that uid with an empty member list (`planner.rs:127-131`); composed for a worker uid it yields a principal in no loop group at all, for which every group-gated path here is closed by the kernel. A worker's credentials are therefore: **uid** its allocated uid; **primary gid** that uid's own group; **supplementary groups** the loop's group alone. The two differ on purpose, because two scopes need two groups — "every lane of this loop" gates the shared rubric and the shared login, while "this lane alone" gates the lane's own tree — and a primary gid set to the loop's group would collapse them, making each lane's tree and each lane's newly created files readable by every sibling lane by default. The launcher's drop is therefore `setpriv --reuid=UID --regid=UID --groups=LOOP_GID --no-new-privs`, and ``sec:permissiontriage:uid-worker`` carries the planner change, the mapping check, and the test row that hold it.

The headline consequence is at the first tier. Under the placement this revision replaces, the rubrics and the registry sat at the deployment uid — the same uid every loop's main session runs at. The principal being judged could therefore write the authorization sources judging it, and the only thing standing in the way was the gate's own always-suspicious boundary on authorization-source edits: a gate refusing the edit that would disable that gate. That is a boundary defending itself, and it holds exactly as long as the thing it defends is working. With the sources at the orchestration loop's uid and mode 0755, a main session cannot write them at all, because it cannot become the orchestration loop's uid. The rule stays in the rubric, and it stops being the only thing there.

The reduction is complete for every loop but one, and the exception should be named rather than discovered. The orchestration loop's own main session can enter its own home and become the orchestration loop's uid, so for that loop the conflation returns in full: it can rewrite the rules it is judged by. What remains against it is what was there before — the always-suspicious estate boundary, the digest recorded on every verdict, and the fact that a crossing into a home is a greppable signature — and the loop that holds it is the loop that already holds estate adjudication authority. Whether to remove even that case by giving the estate tree a uid no loop enters is owner decision 5.

The second tier is a home because a loop is already a home. Nothing new is provisioned: the move to private homes that broke the previous design is the thing that makes this one available, and what changes is only that the home gains a public face and a group-readable face beside its private one.

The third tier is one uid per lane rather than one per loop, and the cost is real — allocation, reclamation, and a launcher to do both. Two properties pay for it. A peer lane cannot edit the clone this lane is about to ship, which a shared worker uid would permit and which no rubric can prevent, since both lanes would be the same principal. And a lane's uid becomes its reaper: everything running at a worker's uid belongs to that lane and nothing else does, so a stop by uid is correct and complete even when the monitor that launched it is gone. Neither property is available at a shared uid at any price.

Three things the tiers do not give, stated here so no later paragraph implies them. They do not separate any loop from the deployment uid, which reaches every home as namespace root through the entry command; the entry is the estate's trusted path and remains one. They do not authenticate the harness input the hook parses, so cwd and session identifier remain assertions carried with a request rather than proofs. And they do not make a loop's own agent trustworthy inside its own tree — a tier bounds what a principal can reach, never what it does with what it reaches.

### The estate tree · `sec:permissiontriage:uid-estate-tree`

The tree holds everything the gate reads that is not one loop's own, and every path in it is readable and traversable by every uid because every uid has a hook that must read it.

- `registry/` — one `NAME.env` per loop, carrying `LOOP_NAME`, `LOOP_SID`, `LOOP_CWD`, `LOOP_UID`, `LOOP_HOME`, `LOOP_WORKER_UIDS`, `LOOP_STATE_ROOT`, and `LOOP_ORCHESTRATOR_RUBRIC`. The registry moves into the tree because it is the surface that decides which role a request resolves to at all, and leaving the one file that assigns identity writable by every identity it assigns is the conflation this design exists to remove. Its modes are the subject of the next paragraph, because they are the one place where this layout and the deployed loader disagree.
- `rubrics/general.md` — the reviewed source of the general rubric. The binary still embeds those bytes and their digest, so this copy is what review edits and what a rebuild reads, and never what a running hook opens. It needs no placement decision and gets one only so that the reviewed bytes stand beside the rubrics that are read from disk.
- `rubrics/owner.md` — the one owner rubric the instance selects. One file for the whole deployment, because the instance variable names exactly one path and the hook loads exactly that one.
- `loops/NAME/orchestrator.md` — the domain rubric governing that loop's main session. It is here rather than in the loop home for the reason the main session is: the session runs at the deployment uid and cannot read into a loop home, and a rubric its reader cannot open is a rubric that grants nothing.
- `hooks/` — the wrapper, the hook binary, the review binary, the topology binary, and the instance file, world-readable and world-executable. They move out of the harness root because the instance names the mode and the binaries are the gate, so both are authorization sources by every test this document applies to the rubrics. The harness settings stay where the harness keeps them and can only name a path; naming a path in this tree is what puts the thing named beyond the session's reach.
- `journals/NAME/` — mode 0700, owned by the deployment uid: that loop's main-session `escalations.jsonl`, its lock, and its empty `classifier-cwd`; the estate loop's directory additionally holds `estate-escalations.jsonl` and its own lock. The owner is the deployment uid rather than the orchestration loop's uid because the writer is the hook running at the deployment uid, and a journal must be writable by exactly its writer. The mode is private because a main session's verdict stream is that loop's own supervision, which is not public evidence the way a lane's run directory is.
- `outboxes/NAME/` — mode 1775, owned by that loop's uid with the loop's group: estate-scoped events from that loop's workers, one 0644 file per event named by its event identifier, written by the worker uid and swept by the loop.

The registry cannot keep the modes the deployed loader requires, and the disagreement has to be resolved in code rather than by wording. `load_registry` reads its own effective uid from `/proc/self` metadata, requires the registry directory to be mode 0700 owned by that uid, and requires every entry to be a mode-0600 regular file with the same owner (`packages/permission-triage/src/role.rs:516-518,530,695-717,731-737`). Under the tiers three different uids' hooks read one registry — a loop's main session at the deployment uid, each of that loop's workers at its own uid, and the estate orchestrator — so "owned by the effective uid" cannot hold for more than one of them, and the measured state's observation that the current registry is exactly what the loader requires stops being reachable the moment the registry is shared.

Two shapes were considered. **A private rendered copy per reader** keeps the loader untouched: each loop, and each worker, holds a 0700/0600 copy at its own uid, rendered from the public tree and verified by digest. It is rejected, and decisively. A copy owned by its reader is a copy its reader can rewrite, so every loop and every lane would own the file that assigns its own identity — which is the failure ``sec:permissiontriage:domain-trust-argument`` names when it says a role a loop can hand itself is not a role, reproduced once per principal. Verifying the copy against the public tree does not save it either, since a reader that must open the public tree to check the copy could have read the public tree in the first place.

**A second accepted shape for the estate registry** is the recommendation: the directory at 0755 and its entries at 0644, both owned by the registered estate uid, with the reader requiring that owner and requiring that no component of the path carry group or other write permission and that every component be owned by the estate uid or by the deployment uid beneath whose home the tree sits. The invariant that replaces "owned by the effective uid" is therefore "owned by exactly one named principal, which is the estate, and reachable only through components no third principal can write". The deployment uid is not a third principal: it is the account whose namespace maps every subordinate uid and which can become any of them through the entry, so excluding it would make the rule unsatisfiable at the proposed `$HOME/loops/estate/` and would buy nothing anywhere it was satisfiable. That is not a weakening, because the old rule was a proxy for a property it could only express while reader and writer were the same uid: nobody but the reader could have written this. Under the tiers the reader is deliberately not the writer — the whole point of moving the registry to the orchestration loop's uid is that a session cannot write the file that identifies it — so the proxy has to be replaced by the property itself, stated over a named owner and checked on every component rather than on the final directory alone. The expected owner is named in the instance file as a decimal uid, so the check has an anchor before the registry parses, and the loader cross-checks it against the estate entry's own `LOOP_UID` afterwards, which catches a repointed instance. World-readable entries expose no secret: an entry carries names, paths, uids, and a session identifier, and a session identifier is corroboration the harness supplies with a request rather than a credential a reader can present. ``sec:permissiontriage:uid-code-bites`` carries this as its own bite, ahead of everything that reads through the loader.

Two of the tree's directories are owned by a uid other than the tree's, which is possible only because changing ownership across uids is a namespace-root act. That happens once, at provisioning, and nowhere in the routine path — which is the property to check when reading the migration below: a routine operation that needed namespace root would be a design defect rather than an inconvenience.

The outbox is per loop, owned by the loop, and sticky, and each of the three answers a different question. Per loop, because the caller loop is then a fact of the path rather than a claim in the record: an estate adjudicator reading an event knows which loop produced it even if every field in the file is wrong. Owned by the loop, because the directory's owner is who is accountable for its contents, and because the loop must be able to sweep it. Sticky, because a drop box its writers can unlink from is a place where evidence disappears between being written and being read, and the sticky bit is exactly the rule that a writer may add and may not remove what is not its own. Group-writable so the loop's workers can write, and world-readable so the estate orchestrator reads it without joining the group and without entering anything.

The sticky bit stops a peer and does not stop a successor, which is a distinct hazard and needs a distinct rule. A uid freed when a lane closes is allocated again, and the next lane holding it would own its predecessor's 0644 outbox files and could unlink them — the same evidence loss the sticky bit prevents between concurrent lanes, arriving through time instead. Closing a lane therefore re-owns that lane's outbox files to the loop uid, or moves them under a closed prefix, before the slot is freed; the run directory is already protected by its rename on close, and this gives the outbox the equivalent. The obligation belongs to the launcher and is stated in [the worker launcher](run-worker.md) as part of what closing means.

The tree is rendered from the orchestration clone's `local/` through the route the rulebooks already use: a reviewed install map, a content-diffed transaction with backups, a staging root, and a preflight that predicts every outcome before anything is written. The property that matters is not the mechanism but what the mechanism forces — an installed byte is traceable to a reviewed commit, and a change to it appears as a content difference rather than as a timestamp. The digest the gate records on every verdict closes the loop from the other end: the installed copy is what the hook reads, the verdict names its digest, and a substitution made outside the transaction is visible afterwards even though the install is a copy and not a link. The render runs as the orchestration loop inside its entry, because that is the uid that owns the destination; the binaries are host-built under the trust boundary that keeps host-executed code reviewable as a text diff, and are installed by the same transaction.

The proposed location is `$HOME/loops/estate/`, a sibling of the loop homes. The sibling placement is the whole of the argument: the parent directory then shows the entire layout in one listing, every home and the tree beside them with its owner visible, so "no journal root inside a loop home" and "no authorization source inside a journal root" become questions a reader answers by looking rather than rules a validator is trusted to have applied. The name must be reserved in the loop-name grammar so no loop can be provisioned onto it. A location unrelated to the homes satisfies every check the code performs and loses only that property, which is why it is the alternative rather than the default; the literal path is owner decision 2.

### The loop home · `sec:permissiontriage:uid-loop-home`

The home goes from 0700 to 0711 and gains four named subtrees. Every mode below is stated, including the two intermediate directories, because every traversal this design relies on passes through them and an unstated mode on `workers/` or `runs/` would close a path the tables above assume is open.

|Path|Owner|Group|Mode|Holds|
|----|-----|-----|----|-----|
|`LOOP_HOME`|loop|loop|0711|The four subtrees below: traversable by every uid, enumerable by none.|
|`private/`|loop|loop|0700|Clone, memory, keys, the loop's own adjudication and journal work. Closed to everything but the loop.|
|`shared/`|loop|loop|0750|What the loop marks readable by its own workers, and nothing else.|
|`shared/permissions/domain.md`|loop|loop|0640|The worker rubric: what this loop's workers may touch routinely.|
|`shared/logins/`|loop|loop|1770|The Claude credentials directory and the link to the shared Codex sign-in, at 0660. The one write grant, argued below.|
|`workers/`|loop|loop|0710|One directory per live lane. The group traverses to a lane it can name and cannot enumerate its peers.|
|`workers/LANE/`|loop|that lane's own gid|0750|The lane's clone at the worker's uid, its loop-owned home, its brief and `identity.env` at 0640, and the monitor's lock.|
|`runs/`|loop|loop|0755|One run directory per live lane, plus `table.tsv` and the closed-run archive.|
|`runs/UID/`|that lane's uid|that lane's own gid|0755|Events, output, last message, run report, and the worker's escalation journal.|

Two directories carry the distinction the design leans on, and it is worth being exact about what it grants: traversal is the permission to walk a path already known, and enumeration is the permission to discover what is there. `LOOP_HOME` at 0711 and `workers/` at 0710 grant the first and withhold the second, so a worker reaches its own lane because `identity.env` names it and cannot learn that a clone, a keyring, a memory directory, or a sibling lane exists. No path-prefix rule expresses that distinction, and no rubric sentence enforces it.

What a worker may read is a named subtree rather than a mode exception inside a private one. An earlier draft of this section put the worker rubric and the logins inside `private/` and opened that directory to group traversal to reach them; a reviewer is then asked to hold in mind that a directory called private is partly not, and `private/` stops meaning one thing. With `shared/` the boundary is legible at the directory level and `private/` returns to 0700, which is the strictest form and the one that needs no explanation. The cost is that a worker can enumerate `shared/`, which holds only what it may read anyway.

`workers/LANE/` is owned by the loop and grouped to that one lane, not owned by the lane. Ownership of a directory is the permission to unlink what is inside it, so a lane that owned its own tree could remove its `identity.env`, its brief, or the settings that register the classifier hook — the three files there that exist precisely to be unremovable by it. Grouping it to the lane's own gid rather than to the loop's keeps a sibling lane out: every lane of a loop shares the loop's supplementary group, so a loop-grouped lane tree would be readable by every other lane of that loop, which is the peer exposure this tier exists to prevent.

`identity.env` is owned by the loop and read-only to the worker because it is data about the worker rather than a claim by it. That is the same distinction ``sec:permissiontriage:role-prompt-carriage`` already draws when it sends the role to the classifier as a hook-derived line rather than as an environment value: a fact about a caller is worth exactly as much as the principal that wrote it.

`shared/logins/` at 1770 is the one place a worker writes inside its loop's tree, and the grant is forced rather than chosen. The harness rewrites its own stored login when a token refreshes, so a credentials directory linked read-only into a worker home leaves two outcomes and no third: either the worker can write it, or every lane long enough to cross a refresh boundary fails there. Granting it is the smaller cost, and it should be stated as what it is rather than left to a reader to infer from a mode. It costs a denial surface and no escalation: a principal that can read a token can already use it, so being able to replace it adds the ability to break the loop's sign-in, not to exceed it. What makes it acceptable is that it is bounded and named — one directory, holding the credential the worker already reads, inside the subtree whose whole purpose is what the loop hands its workers — rather than a write bit somewhere in a tree called private. Refusing the grant and accepting refresh failures is the alternative, and it is owner decision 6. The directory is sticky and the loop opens the credential without following a final symbolic link, because a plain 0770 lets a worker unlink the file and leave a symlink in its place, which the loop then follows on its own next read — a write grant that becomes a redirection of the grantor. The grant assumes the refresh writes the credential in place: with the directory sticky and the files the loop's, a worker may rewrite a login and may not unlink or rename over one, so a harness that refreshes by writing a temporary file and renaming it fails here with a permission error. That is the same obligation the pre-created writable children under `.claude/` already carry, and it points the same way — loud and repairable rather than silent — but it is an assumption about the harness and belongs beside the mode rather than inside it.

The run directory is public, and the reason is about which privilege the routine path runs at. Two readers want a lane's evidence routinely: a log consumer and the deployment session. If the run directory were private to the loop, both would read it through the entry command, which is namespace root before it drops — so the estate's most ordinary observation would run at the one privilege that can read every home. The entry command's own boundary note names a bare namespace-root crossing as one of two signatures a reader can grep a transcript for; a design producing one of those per log poll makes the signature worthless. A world-readable run directory keeps namespace root for provisioning alone. The cost is stated rather than hidden, and it is larger than the transcript alone. The events file is the worker's whole transcript, readable by every uid on the host, which on this workstation means every uid in the deployment's own subordinate range. Beside it the worker's journal carries a `command` field, and `packages/permission-triage/README.md` warns in the review command's own contract that command text may contain credentials — so a world-readable journal turns that warning from a caution addressed to a reviewer into a host-wide exposure. The mitigation is the estate's standing rule that agents never handle credentials: a worker that never receives a secret cannot put one in a command, and every credential path in this estate is an owner-run step precisely so that no agent's transcript can carry one. That is a mitigation and not a guarantee, which is why it belongs in this paragraph rather than in a reader's inference. A dedicated observer group at 0750 buys the confidentiality back for the price of a group and its membership, and is owner decision 4.

That public run directory has a consequence for the journal checks, and it is the useful kind. The current rule requires a 0700 root and a 0600 journal file, and a public run directory satisfies neither. Those modes were protecting two properties at once: that nobody but the writing uid may write the evidence, and that nobody else may read it. For a run directory the second is given up deliberately, and the first must still hold exactly. So the check becomes ownership by the effective uid with no group or other write bit, which is the property that was always load-bearing; a journal in a loop or estate root keeps 0700 and 0600, because nothing asks those to be public. The difference between the two cases is then stated by the deployment rather than assumed by a constant.

The worker rubric lives in the loop home and the orchestrator rubric in the estate tree, so a loop can write one of the two rubrics that govern it. That is safe under one rule, which the hook must implement: the estate-held orchestrator rubric is the bound and the loop-held worker rubric is a narrowing inside it. At run time nothing new is needed — the conservative precedence already makes an independent suspicious property beat any grant, so a worker-rubric clause naming something outside the loop's domain cannot lift a class. At deployment the containment check cannot run where the rest of assembly runs, and pretending otherwise would put a check in the design that its own principal could not perform: the assembler runs at the deployment uid, and the worker rubric is 0640 inside a 0750 `shared/`, which this subsection has just argued the deployment uid cannot reach. So the check runs as the loop uid through the loop's entry, as a mode of the assembler, and publishes its verdict and the rubric's digest into the loop's world-readable run tree; the deployment-uid assembly then requires that published verdict to exist and records its digest in the deployment record. What that chain does and does not give should be said exactly. It does not let the deployment uid verify the rubric's content or its freshness, because it can read neither. It does bind the content check to a digest, and the hook records the digest of the rubric it actually loaded on every verdict — so a rubric substituted after the check appears as a digest in the acceptance window's verdicts that no published verdict covers, which is a review-time detection rather than a deployment-time refusal. A loop may therefore narrow its workers and may not widen them past itself, with the deployment half of that enforced one principal removed. The principal that publishes the verdict is the principal being checked, and the chain should be read accordingly: it detects a rubric substituted after the check, because the digest the hook records then matches no published verdict, and it does not detect a loop that publishes a passing verdict for a widening rubric it goes on to serve, because those digests agree. The deployment half is therefore advisory, and the widening it would catch is closed by review of the rubric text where every other authorization source is reviewed.

Until the launcher dispatches a loop's lanes, a lane still runs at the deployment uid through the Codex lane driver in a clone under the deployment's temporary root and reaches the servers with the loop's worker key through the loop's Codex home, so the worker rubric of that form names, inside the lane roots, the loop's two worker aliases and the candidate ref the lane publishes to the hub; the statement that a worker authenticates to no server describes the launcher tier and holds from migration step 9 on.

Two services stay outside the tiers on purpose. The lane gateway is a deployment-uid service driven from the loop's main session, and its registrations name only mirrors the deployment uid can read, since a path under a loop uid's home is unreadable to it; and a moved loop imports a candidate by fetching the lane's tip from the hub over its own alias, because a lane clone on the host is unreadable to the loop's uid and the hub is the one place both principals reach.

### The worker uid · `sec:permissiontriage:uid-worker`

Each loop's entry declares `LOOP_WORKER_UIDS=BASE:COUNT`, an inclusive run of uids reserved to that loop's lanes, required to be disjoint from every other block, from every registered `LOOP_UID`, and from the deployment uid. Deployment validation checks that pairwise, exactly as it already checks journal roots.

Declaring the block rather than deriving it from the loop's uid is the same trade the previous revision made when it chose a registry field over a name-to-path convention for the domain rubric, and for the same reason. A derivation needs no field and no check, and its safety property — that no two loops collide — would then rest on an arithmetic invariant nothing verifies, held by a numbering convention compiled into a binary, over an estate whose loop uids were assigned by hand. A declared block is checked where roots are checked, and the estate writes its numbering where it already writes its numbering.

Which slot is live is the launcher's record in the loop's public run tree, and it is evidence rather than authority. The gate resolves a worker's loop from the registered block its effective uid falls in and consults no table to do it, so a stale, damaged, or forged table changes a journal field and no decision. That is what makes the identity safe to hand out: a loop can only name uids the estate already gave it, and the sentence in ``sec:permissiontriage:domain-trust-argument`` that a role a loop can hand itself is not a role stays true with workers in it.

A block must be validated against the mapping the deployment actually has, not against a constant. Ownership changes and the drop itself only work for uids the owner's user namespace maps, and that mapping comes from the deployment account's entries in `/etc/subuid` and `/etc/subgid`, which podman reads when it builds the namespace. A block checked against a compiled range of 1000 through 65535 can therefore validate at deployment and still fail at `chown` or at `setpriv` when a lane launches, which is the worst place for it to fail: after a tree has been built and before anything runs. Validation reads both files for the deployment account and requires every uid in the block, and the gids beside it, to be no greater than the count of the deployment account's subordinate range, because a rootless namespace maps that range onto namespace ids 1 through the count and every number this design writes — the loop uids, the worker blocks — is a namespace-internal one. The same check covers the loop uids and the loop gids the supplementary group depends on, since a gid beyond the subordinate gid count fails exactly as an out-of-range uid does and the two files are configured separately.

The arithmetic of the proposed default is worth writing out, because "about a hundred" is not a number a validator can check. Blocks of 256 starting at 40000 place base `40000 + 256k`, and the last block whose top stays inside 65535 is base 65088 at `k = 98` with top 65343 — 99 loops, not a hundred. Whether 99 is enough is a question about the estate rather than about the code, and the answer is that it is enough by a wide margin for an estate with four registered loops; if it ever stops being, the count per block is the value to reduce, since a loop's concurrent lanes are single digits and 256 was chosen to make exhaustion mean a leak rather than a busy day.

### Identity under the uid factor · `sec:permissiontriage:uid-identity`

Role resolution keeps its three values and its conservative failure and gains one input ahead of the others.

1. An effective uid inside a registered worker block resolves to that loop with the role `orchestrator-subagent`. The request's working directory is not consulted. The uid is the one the code already reads for its ownership checks — the owner of `/proc/self` (`packages/permission-triage/src/role.rs:516-518`) — which is kernel-supplied about the reading process itself and is not carried in the request, so naming its source is part of the rule rather than an implementation note.
2. Otherwise, a request at the deployment uid whose normalized `cwd` equals a registered `LOOP_CWD` and whose `session_id` equals that entry's `LOOP_SID` resolves to that loop, as `orchestrator-subagent` when a subagent signal is present and `orchestrator` otherwise.
3. Everything else resolves `unknown`.

|Caller|Effective uid|What decides it|Role|
|------|-------------|---------------|----|
|The loop's main session|deployment uid|Registered launch directory and matching session identifier.|`orchestrator` of that loop|
|A Claude worker|that lane's own uid|The registered block the uid falls in.|`orchestrator-subagent` of that loop|
|A Codex worker|that lane's own uid|The same block — but no request of its ever reaches this hook.|No verdict; see below|
|An in-session subagent|deployment uid|Launch directory, session identifier, and the subagent signal.|`orchestrator-subagent` of that loop|
|Another loop's session at this loop's launch directory|deployment uid|The session identifier matches no entry for that directory.|`unknown`|

The Codex row is the one that shows what the tiers are for. This hook is a Claude Code `PreToolUse` hook; a Codex lane's driver has its own approval machinery and raises nothing here, so the gate returns no verdict for such a worker at all. Under the placement this revision replaces, that was a hole with nothing behind it — a Codex worker ran at the deployment uid, in a clone at the deployment uid, with the same reach as the session that dispatched it, and the only thing between it and a peer loop's tree was its brief. Under the tiers it is a hole with a floor: a Codex worker is confined by the same modes as a Claude worker whether or not any classifier ever sees a request. The containment stops depending on the gate, which is the strongest thing that can be said for a boundary the kernel keeps.

The uid factor does nothing for the three deployment-uid rows, because every such caller shares that uid, and the working directory and session identifier remain the whole of the decision. That is why rule 2 requires the session identifier to match rather than treating a mismatch as a flag on a granted role. The current rule retains the checkout-selected loop and records `stale_session=true`, and that concession made sense when the checkout was a real tree holding the loop's material and the identifier was corroboration of a strong signal. A launch directory holds nothing, so the identifier is not corroboration — it is half of a weak signal, and half of a weak signal is not a grant. Requiring both costs one loud, repairable failure: a rotated session resolves `unknown` until its entry is rewritten. It removes the case in which an unexplained identifier still carries a loop's orchestrator role, and step 4 of ``sec:permissiontriage:enforce-flip`` already refuses to complete an acceptance window containing an unexplained stale flag — so the flip already treats this state as unacceptable, and this moves the same judgment from the review to the request. `LOOP_SID` becomes required at deployment validation.

That change narrows four of the five rows and could widen the damage in the fifth, so it is held conditional on a measurement this design has not taken. Rule 5 selects the subagent role only after the session checks have passed, so an in-session subagent whose `session_id` is not its main session's registered identifier would resolve `unknown` under the new rule and be denied under enforce — turning a narrowing into an outage for the one caller shape that is neither a worker nor a main session. The measurement is listed as pending in ``sec:permissiontriage:private-home-measured-state``, and the bite that requires the identifier is written to depend on it: if a subagent carries its main session's identifier the rule lands as stated, and if it does not, the rule admits a caller that carries a subagent signal and whose identifier matches no registered entry, still refuses one whose identifier is another entry's, and still resolves `unknown` for a caller with no subagent signal and an unmatched identifier. Without that restriction the fallback branch would restore the grant this change exists to remove: a plain session at a registered launch directory taking that loop's orchestrator role on an identifier nobody registered. Deciding that in advance of the measurement would be choosing between a regression and a weakened rule without knowing which one is on the table.

The lane-root field the previous revision needed is retired by rule 1, and so is the caveat that came with it. That design registered one lane root per loop so a lane clone's working directory could confer identity, and had to concede that a directory beneath a registered root confers that role to whoever creates one, because every loop's main session shared the uid that could create it. The uid factor removes the field and the concession in one step: a lane's identity is the uid it runs at, which it cannot choose, and its working directory stops being an identity surface at all. A revision that deletes a field, a validation rule, and an acknowledged weakness together is the one to prefer.

A worker takes `orchestrator-subagent` rather than a fourth role for the reason ``sec:permissiontriage:subagent-domain`` gives: the grant is justified by a property of the context — one that ingests file contents, tool output, and network text with no supervising turn between ingestion and the next tool call — and a dispatched lane is that context exactly. What changes is that the four effects the grant withholds are now withheld twice. Publication to the loop's hubs, writes to the loop's memory, lane dispatch, and use of the loop's server account are each unreachable from a worker uid: there is no git or signing key in the worker home, no write into `private/`, no entry command available to a dropped uid, and no server-account credential anywhere a worker can reach — the one credential it does reach is the loop's stored model login, which is the account the lane is meant to run as. Where the grant and the kernel agree, a misclassification of that request costs nothing, which is the best position a policy boundary can be in.

### What stops needing to be said · `sec:permissiontriage:uid-filesystem-facts`

Peer boundaries. The hook computes peer checkout boundaries from the registry snapshot and tells the classifier about them, because a worker at the deployment uid could open a peer's tree and only the gate would object. A worker uid cannot open a peer loop's home, its private tree, its workers' trees, or write into its run directories. The rubric sentence stays — a boundary worth enforcing is worth enforcing twice, and the classifier's verdict is also evidence — but its justification changes from "this is the only thing stopping it" to "this is the second thing stopping it", and the deployment's own argument should say which, because a premise that has become a belt-and-braces check should stop being counted as a premise.

The uid factor covers workers and does nothing for callers at the deployment uid, and this layout makes that gap wider rather than narrower. Peer boundaries are built today from each other entry's checkout and state root alone (`packages/permission-triage/src/hook.rs:1044-1058`); a peer's `LOOP_HOME` is in neither list. With `runs/` world-readable, any deployment-uid caller — a peer loop's main session, an in-session subagent of one — can read every other loop's complete worker transcripts, and the classifier raises nothing, because the path it would object to is not a boundary it was given. The uid argument does not reach this case: every deployment-uid caller shares the uid, so only the rubric boundary is available, which is exactly the situation where the rubric boundary has to be right. Peer roots therefore gain each registered peer's `LOOP_HOME`, so a deployment-uid read of a peer's run directory classifies estate rather than passing unremarked, and the layout-checks bite in ``sec:permissiontriage:uid-code-bites`` carries that sentence and the file it changes.

A worker's blindness toward `private/`. The design no longer needs a rule that a worker must not read the loop's memory or keys; it needs a mode, and it has one. The rubric text enumerating those paths becomes a statement of fact about what is unreadable rather than a prohibition — which is the form ``sec:permissiontriage:domain-rubric`` already says a domain rubric takes, and this is the first layout in which that sentence is literally true for the worker case rather than aspirationally true.

The superloop's journal. A worker cannot reach a main session's journal directory, which is 0700 at the deployment uid inside the estate tree, and cannot reach a peer worker's journal for writing. Under the previous layout every journal was reachable by every worker and its integrity rested on the gate refusing the request — that is, on the same gate whose evidence the journal is.

The README's peer-boundary and state-root paragraphs describe the implemented build correctly today and must not be corrected ahead of the code that changes it. The reasoning the previous revision gave for that holds unchanged: a document accurately describing an implemented build does not become false because a design proposes to change the build, and correcting it early leaves it describing a validator that does not exist. Each bite below carries the replacement sentence it makes true.

### The adjudication routes · `sec:permissiontriage:uid-adjudication`

Loop-scoped first, and the route is the implemented one rather than a new one. A worker's suspicious verdict is journaled into its own public run directory and denied; the loop's main session learns of it from the launcher's waiter, which returns a distinct status for a waiting escalation; the session reads the event where the worker wrote it, adjudicates in its own journal, and **re-issues the approved work as its own request**. The worker consumes nothing. That is what the build does today and what its documentation states it does: suspicious loop-scoped work from a worker, including a Codex lane or an in-session subagent, is reviewed by its loop's main session, which must re-issue approved work as its own request. One consequence of the tiers belongs beside this route: the main session can re-issue only work it can itself perform, and the lane's clone is 0700 at the worker's uid, so an escalation on work inside the lane's own tree has no re-issue path. That case ends the lane rather than unblocking it, which is the conservative outcome and is a reason to keep a worker's in-tree work inside its domain rubric rather than at the escalation boundary.

A draft of this section proposed the other route — a disposition written into the loop's tree and consumed by the worker's own hook on retry — and it was wrong on the code in three independent places, each of which is a deliberate refusal rather than an omission. The one-shot path reads the **journal**, not a disposition tree (`packages/permission-triage/src/hook.rs:1126-1140`, `packages/permission-triage/src/journal.rs:360-389`). It refuses any caller that is not an orchestrator before it reads anything at all (`hook.rs:1135`, mirrored at `journal.rs:364`). And it refuses an approval whose *source* event was not an orchestrator's (`journal.rs:329-330`). A route that claimed to use "the existing one-shot path" while requiring all three to be lifted was not using it. Lifting them is a design decision with a security cost and not a wording fix: the property those refusals hold is that an approval is bound to a principal whose turns a person can read, and a worker-consumable approval moves the consuming principal to one whose evidence it writes itself. Re-issuing costs one hop — an orchestrator in the same session re-issues after reading the reason — and it is the conservative route, so it is the recommendation. If a worker-consumable disposition is ever wanted, the case must be made for lifting three implemented refusals in a bite of its own, and it must state what the bound becomes, which is: an approval whose consumption record is written by the uid it approves.

A journal mark is unchanged and remains the one adjudicating act. `permission-triage-review --mark` reads a loop's journal in the estate tree at the deployment uid with no crossing at all, and a mark attempted inside an entry fails the root's ownership check (`role.rs:710-715`). That is the correct failure and the reason to keep it: the adjudicating identity cannot be laundered through a uid transition. Estate marks remain refused for the separate reason recorded in item 5 of ``sec:permissiontriage:gate-able-implementation-bites`` — estate adjudicator provisioning is still unspecified, and every estate mark is refused at `journal.rs:299-302` — and nothing in this layout supplies that authority, since ownership of a root has never supplied it.

Estate-scoped second, and the write route needs a bite the previous revision did not name. A worker cannot open the estate journal, which is 0700 at the deployment uid, so without a sink of its own a worker's estate-scoped verdict has nowhere to go and becomes an infrastructure denial under enforce. The sink is its loop's outbox: the worker's hook writes the verdict there as one 0644 file at the worker's uid, adds to a directory it cannot remove from, and records the destination in its own journal. The estate orchestrator's review command reads every registered loop's outbox at the deployment uid — no entry, no privilege, no group membership — and adjudicates as before, once estate adjudication authority exists to adjudicate with. The rest of the routing is unchanged: loop-scoped records still reach only the caller's own journal, and a failed loop sink still never copies its record into the estate journal. What changes is the sentence that used to say an estate event reaches only the estate stream, which was true when every caller could open that stream and is not true of a worker; the bite that writes the outbox carries the replacement.

### Migration · `sec:permissiontriage:uid-migration`

The ordering constraint is that steps 1 and 3 through 6 change layout only and are safe against the deployed parser, step 2 is code already moving, and steps 8 through 10 write registry and instance content only a post-bite build parses. Step 7 is what makes that true and is easy to leave out: the hook binaries are installed by step 4's transaction, which runs before the bites land, so without an explicit reinstall the deployment would hold a pre-bite gate reading post-bite content. The previous revision's review recorded the same omission, and it is carried forward here rather than rediscovered a third time. Step 9 additionally waits on the launcher's first bite.

1. Repair the registry entry modes. Owner-run, and independent of this design. Verification: every entry is a mode-0600 regular file owned by the deployment uid and the directory is 0700, read back with a stat of each.
2. Land the parser bite accepting `LOOP_UID` and `LOOP_HOME`. This is the first code step and it is already in flight; every later step's verification depends on it, because until it lands the estate's own registry drops its two moved entries and every request resolves `unknown` before identity is attempted. Verification: an entry carrying both keys parses and resolves identically to one without them, and the live registry loads whole.
3. Provision the estate tree. Owner-run, namespace root, once: the skeleton at the orchestration loop's uid, the journal directories at the deployment uid at 0700, the outboxes at each loop's uid at 1775 with the loop's group. Verification: a stat of every path against the tier table, and a write probe from each tier's uid proving the intended writer can write and the others cannot.
4. Install the authorization content through the render route. Superloop-run as the orchestration loop inside its entry. Verification: the preflight predicts every outcome, then a digest comparison between installed bytes and the reviewed git-tracked bytes.
5. Rewrite each loop's orchestrator rubric and worker rubric for the new layout. Owner-run for the estate copy, on text the loop drafts. The facts that are now false are the ones the previous revision found and two more: the checkout, the lane clones, the journal, the state root, the worker tree, and the run directory. A domain rubric whose facts are false grants the wrong set. Verification: every absolute path the rubric states resolves, the worker rubric's roots lie inside the orchestrator rubric's domain, and both digests are recorded in the declaration ``sec:permissiontriage:enforce-flip`` step 1 requires.
6. Reshape each loop home: 0711, with `private/`, `shared/`, `workers/`, and `runs/` at their stated modes, owners, and groups. Superloop-run for the content, owner-run and namespace root for the ownership and mode changes. After the move and before any signed operation the loop's `gpg-agent` and `scdaemon` are ended inside the entry, because the running agent still serves the directory it was started in; a verification script fed to the entry on standard input carries `-n` on every `ssh` call, because an `ssh` call without it reads the rest of the script as its own input. Verification: the mode table, plus a read probe from a worker uid proving `shared/` is readable, `private/` is not, a peer lane's tree is not, and `workers/` is traversable and not enumerable.
7. Reinstall the hook binaries from the post-bite build through the same render route, and read back the installed digests against the build. Owner-run. Verification: the deployment record's binary digest equals the built artifact's, and a probe request resolves an entry carrying the extended grammar rather than rejecting it.
8. Allocate the worker blocks and rewrite each registry entry to the extended grammar, at the estate registry's modes. Owner-run; a registry write is estate-scoped. Verification: the assembler's check mode, which exercises the real parser, the real block disjointness against the deployment's subordinate mapping, and the real layout rules rather than a reading of the file.
9. Move one loop's lane dispatch to the launcher. Superloop-run, one loop first. Verification: one real launch of a read-back lane, whose run directory is readable at the deployment uid without entering, whose clone and brief are unreadable from a peer lane's uid, whose worker reads the shared rubric and writes the shared login, and whose slot is reclaimed when the lane closes.
10. Rewrite the live instance: the missing mode, the estate uid the registry loader checks against, and the estate tree's paths for the owner rubric, the registry, the state root, and the hook binaries. Owner-run. Verification: a probe request through the installed wrapper produces zero stdout bytes, exit zero, and one correlated schema-2 verdict in the expected journal — the audit-silence read-back ``sec:permissiontriage:enforce-flip`` step 3 already requires.

After step 10 the owner procedure resumes unchanged from its step 2: the window, the limits, and the observation are not altered by this layout, only the paths and the principals they are measured over. One measure changes in kind and should be declared before the window rather than explained after it, and its timing should be stated exactly rather than optimistically. A lane launched through the launcher carries a resolved role where it previously resolved `unknown`; a lane of a loop that has not yet moved still resolves `unknown`, because nothing about it has changed. Step 9 moves one loop on purpose, and the launcher's own first bite defers the subcommand that closes a lane, so the estate will run staggered for as long as that takes. The zero unknown count ``sec:permissiontriage:enforce-flip`` step 4 requires is therefore reachable at the end of the migration and not after step 10, and an acceptance window opened before every loop has moved will fail on the loops that have not — which is the correct outcome and worth stating in advance rather than discovering in a review.

### Code consequences · `sec:permissiontriage:uid-code-bites`

Gate-able bites in dependency order. No bite authorizes installation or changes a live instance. All nine are on main: bite 1 as 25707a96, bite 2 as ab5fbde6, bite 3 as 2ebfa5ef and 7929462e, bite 4 as 7ddbb0d8, bite 5 as 4317624b and 0e9d5d51, bite 6 as c2018941, 5a20f383 and c933f851, bite 7 as 05b1fc2f and 56a5715d, bite 8 as e4de5a29, and bite 9 as ad8f571e and a32fbe34; what follows is the owner procedure of ``sec:permissiontriage:enforce-flip`` under the decisions of ``sec:permissiontriage:uid-owner-decisions``.

1. **Accept `LOOP_UID` and `LOOP_HOME` in the closed grammar.** Landed as 25707a96; its files, tests, and replacement sentence are unchanged from the previous revision. It is listed here because everything below depends on the estate's current registry parsing at all, and because the divergence that made it necessary is the argument for the rule that any field the registry's writers add is added to the parser in the same change: two authorities over one grammar drifted once, and the drift was invisible until it was read.
2. **A second accepted shape for the estate registry.** Files: `packages/permission-triage/src/role.rs`, `packages/permission-triage/src/tests/hook.rs`, `packages/permission-triage/tests/hook.rs`, `hooks/permission-triage`, `packages/permission-triage/README.md`. This bite comes before every other reader-side change because nothing below resolves an identity until the registry loads. `load_registry` gains the estate shape beside the one it has: a directory at 0755 whose owner equals the decimal uid the instance declares, entries at 0644 with that same owner, no component of the path carrying group or other write permission and no component owned by a third principal, the deployment uid beneath whose home the tree sits not being one, and a cross-check after parsing that the declared uid equals the estate entry's `LOOP_UID`. The private 0700/0600 shape stays accepted unchanged, so a deployment that has not moved its registry is not broken by the bite. Tests: the estate shape loads at three different effective uids, none of them the owner; a directory or entry owned by anyone but the declared uid rejects; a group-writable or world-writable directory, entry, or ancestor rejects; a declared uid disagreeing with the estate entry's `LOOP_UID` rejects after parsing; the private shape still loads for its owner and still rejects a foreign owner; a 0644 entry under the private shape still rejects, so the two shapes cannot be mixed within one registry. Replacement sentence for the README's registry paragraph: "A configured registry is accepted in one of two shapes — private, a mode-0700 directory of mode-0600 entries owned by the reading process's effective uid; or estate, a mode-0755 directory of mode-0644 entries owned by the uid the instance declares, with no component of the path carrying group or other write permission and no component owned by a third principal, the deployment uid beneath whose home the tree sits not being one, and the declared uid cross-checked against the estate entry's `LOOP_UID` — and an unavailable, unsafe, over-cap, or otherwise unreadable registry conservatively resolves the request as `unknown`."
3. **Worker blocks and uid identity.** Files: `packages/permission-triage/src/role.rs`, `packages/permission-triage/src/hook.rs`, `packages/permission-triage/src/tests/hook.rs`, `packages/permission-triage/tests/hook.rs`, `packages/permission-triage/README.md`. `LOOP_WORKER_UIDS` parses as `BASE:COUNT`, both decimal; an effective uid inside a block selects that loop and the subagent role before any working directory is considered. Deployment validation checks each block against the deployment account's entries in `/etc/subuid` and `/etc/subgid` rather than against a compiled range, because a uid outside the namespace's mapping fails at `chown` and at `setpriv` regardless of what a constant permits. Tests: a uid inside a block resolves that loop as a subagent from an unregistered working directory, from a registered peer's launch directory, and with no session identifier at all; a uid inside no block falls through to the launch-directory rules; overlapping blocks, a block containing a registered `LOOP_UID`, and a block containing the deployment uid each fail deployment validation; a block reaching outside the mapped subordinate uid range, and one whose gids reach outside the mapped subordinate gid range, each fail against fixture mapping files; a block whose parse fails rejects the entry whole. Two replacement sentences for the README. For the role-resolution paragraph: "The bounded parser accepts one `LOOP_NAME`, one `LOOP_SID`, one absolute dot-component-free `LOOP_CWD`, one `LOOP_UID`, one absolute dot-component-free `LOOP_HOME`, one `LOOP_WORKER_UIDS` block, one `LOOP_STATE_ROOT`, and one `LOOP_ORCHESTRATOR_RUBRIC`; a request whose effective uid lies in a registered block resolves to that loop as `orchestrator-subagent` without consulting its working directory, and every other request resolves from the working directory and session identifier as before." For the sentence stating that role evidence comes only from hook input and parsed registry bytes, which the uid factor makes false: "No environment value participates as evidence in a permission decision; role evidence comes from hook input, parsed registry bytes, and the reading process's own effective uid, which the hook reads from the owner of `/proc/self` and which no request can assert."
4. **Require the session identifier for a launch-directory role.** Files: `packages/permission-triage/src/role.rs`, `packages/permission-triage/src/tests/hook.rs`, `packages/permission-triage/README.md`. This bite is conditional on a measurement it must take first: what `session_id` an in-session subagent carries relative to its main session's registered `LOOP_SID`, recorded as pending in ``sec:permissiontriage:private-home-measured-state``. If a subagent carries its main session's identifier, the retained grant of rule 4 becomes `unknown` as stated. If it does not, the rule admits a caller that carries a subagent signal and whose identifier matches no registered entry, still refuses one whose identifier is another entry's, and still resolves `unknown` for a caller with no subagent signal and an unmatched identifier, because the alternative is denying every in-session subagent under enforce — a regression dressed as a narrowing. `LOOP_SID` becomes required at deployment validation either way. `stale_session` stays in the schema and is always false: schema 2 records are compared across an acceptance window, so removing a field invalidates the comparison, and a field that is always false is cheap to keep until a schema 3 has another reason to exist. Tests: the measurement is recorded as a fixture with its date; a matching identifier resolves; a rotated identifier resolves `unknown` rather than recording a flag; an absent `LOOP_SID` fails deployment validation; another entry's identifier still resolves `unknown`; an in-session subagent resolves as the measurement requires and the test names which branch it asserts.
5. **Journal roots under the tiers.** Files: `packages/permission-triage/src/role.rs`, `packages/permission-triage/src/journal.rs`, `packages/permission-triage/src/bin/permission-triage-assemble.rs`, `packages/permission-triage/tests/assemble.rs`, `packages/permission-triage/src/tests/journal.rs`, `packages/permission-triage/README.md`. ### Owner decisions · `sec:permissiontriage:uid-owner-decisions`

These are rules of the estate rather than facts of the code. Each carries the default this design proposes.

1. **The worker-uid block scheme.** Default: a declared `LOOP_WORKER_UIDS` of 256 slots per loop, with bases assigned in ascending order from 40000 in steps of 256, checked pairwise at deployment and checked against the deployment account's subordinate uid and gid mappings rather than against a compiled range. The last block whose top stays inside 65535 has base 65088, so the scheme holds 99 loops, and every worker uid sits legibly above every loop uid, which lets a number alone say which tier it belongs to. The count is far above any loop's concurrent lanes on purpose: a block large enough that exhaustion means a leak rather than a busy day turns the refusal into a diagnosis. If the mapping the deployment actually has is narrower than the scheme assumes, the mapping is the thing to widen or the base is the thing to move, and the validation is what makes the choice visible before a lane fails at launch.
2. **The estate tree's location.** Default: `$HOME/loops/estate/`, a sibling of the loop homes, with the name reserved in the loop-name grammar. The property being bought is that one listing shows the whole layout with each owner visible; an unrelated location passes every code check and loses only that.
3. **Whether the two unmoved registered loops are live loops for this gate.** They carry no `LOOP_UID` or `LOOP_HOME`, so they have not been moved, and under the tiers they now need a home, a uid, a block, an orchestrator rubric, and a worker rubric before assembly can validate the estate at all. Default: provision them, since step 1 of the owner procedure requires every live loop registered; the alternative is removing their entries until they are live, which is a decision about whether they are live and not about this gate.
4. **Whether a run directory is world-readable.** Default: yes, with the consequence stated — the events file is the worker's whole transcript and every uid on the host can read it. The alternative is a dedicated observer group at 0750, which buys the confidentiality back for a group and a membership to maintain, and which keeps the important half either way, since the run directory is readable without namespace root in both.
5. **Whether the estate tree is writable through the orchestration loop's own entry.** Default: yes, which leaves that one loop able to rewrite the rules it is judged by, defended by the always-suspicious boundary and the recorded digests exactly as every loop was before. The alternative removes the last instance of the conflation this design exists to remove: give the estate tree a uid no loop enters, and make its writes a provisioning act rather than a loop act. It costs one more provisioned principal and one more entry path, and it is the only remaining change that would make the reduction complete.
6. **Whether a worker may write its loop's stored login.** Default: yes, through `shared/logins/` at 1770 with the login files at 0660, as the single stated write grant a worker holds inside its loop's tree. The alternative is a read-only link, under which the harness's own token refresh fails and every lane long enough to cross a refresh boundary ends there. The grant adds a denial surface and no escalation, since a principal that can read a token can already use it; what the default buys is that the estate chooses where the write lands rather than discovering it as a class of lane failure.
