# Provider-door self-healing · `proposal:doorselfheal:provider-door-self-healing`

Status: DRAFT — programme requirements are fixed; the numerical thresholds and operating mechanisms identified as proposals remain subject to owner review.

## Purpose and decision provenance · `sec:doorselfheal:purpose-and-decision-provenance`

The door-recovery programme requires every eligible root-full server to inspect its own forward from a configured port-forward provider through its own provider tunnel, repair a missing or ageing grant without attendance, notify the estate when coordinates change, emit an independent external beacon, and put that beacon first in diagnosis. The separate door-redundancy programme requires additional routes with different providers or mechanisms, because repairing one provider's grants cannot remove that provider as a common failure domain.

Those programme requirements govern this document. The proposed choices are a five-minute self-check, a seven-day renewal window, three-run failure escalation, a two-minute beacon with a three-interval silence threshold, the transactional reconciliation order, a durable owner-correspondence letter as the endpoint-change record, and a workstation-side client reconciliation step. Each proposal is replaceable without reopening the required self-check, beacon, diagnosis, custody, or redundancy boundaries.

This model extends [per-account WireGuard routing](per-user-wireguard-routing.md): the provider allocation remains aligned with the inbound listener, but the binding becomes continuously reconciled rather than a manually renewed inventory fact. It also uses the timer, quiet-scan, and journal conventions of [correspondence-watch](../../infra/correspondence-watch/README.md) without assigning judgment to that scanner.

## Failure classes · `sec:doorselfheal:failure-classes`

**Provider-side grant loss without notice.** A measured incident erased several independent grants at once while their provider tunnels and the provider API continued to work. The authoritative listing returned no grant, so a local listener could remain healthy on its old port while the provider no longer delivered that port. The loop must therefore trust a successful, allocation-scoped provider listing over remembered local state; asking the provider why the registry changed may improve history, but it neither restores reachability nor bounds recurrence.

**Grant expiry.** The observed grant lifetime is approximately thirty days, which turns a forgotten renewal into a predictable door outage. Expiry differs from an unannounced wipe only in that the deadline is visible beforehand. Renewal ahead of the deadline removes clock-edge risk and gives repeated timer runs time to survive a temporary API failure.

**Path failure.** A valid grant can coexist with a failed provider tunnel, wrong policy route, stale runtime listener, stale persisted listener, or broken inbound path. A grant listing alone is therefore not an end-to-end health statement. The server can reconcile the provider record, the live listener, and the persisted listener locally, but only an independent external probe can prove that a roaming packet crosses the public path.

**Site-uplink loss.** Both co-sited servers can be healthy while their shared external connection is unavailable. From a roaming client, that condition, a provider registry wipe, a listener mismatch, and a workstation routing error all reduce to the same symptom: no handshake. An authenticated outbound beacon using the ordinary site egress separates the classes: fresh beacons rule out a total site-uplink loss and direct attention to the provider door, while simultaneous silence from the co-sited servers makes the shared site path the first suspect.

Self-healing and redundancy solve different parts of this set. The loop shortens a known-shape provider loss from an operator-discovery interval to a timer interval; an independent door preserves entry when the provider API, the provider tunnel, the whole provider, or the site is unavailable. Together they offer a bounded automatic repair for the measured failure and a route around failures that repair cannot reach, which is a stronger availability control than a provider inquiry with no restoration or recurrence guarantee.

## Self-check loop · `sec:doorselfheal:self-check-loop`

Each eligible server runs a root-owned oneshot service from a systemd timer. The script takes a non-overlapping lock, reads root-only instance configuration and the provider token in place, forces the allocation-scoped listing through that server's own provider tunnel, and distinguishes an authoritative empty result from transport, authentication, parsing, or ambiguous-result failure. Only an authenticated successful empty listing means “missing”; an unavailable or malformed API never licenses a new grant.

A check treats the door as healthy only when exactly one allocation grant exists beyond the renewal window, the live inbound WireGuard listener uses its assigned port, and the persisted listener configuration names the same port. A healthy result changes no provider or local state. The service manager's successful completion and timer timestamps are its liveness record; like a quiet correspondence scan, the script emits no application journal event merely to repeat that nothing changed.

When the grant is missing or expires inside the proposed seven-day window, the script requests a replacement through the same tunnel and validates the returned allocation, port, and expiry before touching the listener. Seven days is long compared with the check cadence but short compared with the approximate grant lifetime: it supplies many retries through an API disturbance without causing frequent churn. If the provider permits overlapping grants, the old path remains until the replacement is validated; if it requires revoke-then-grant, the implementation records that bounded cutover explicitly and never destroys the only grant merely because a listing failed.

The replacement response becomes desired state. The script prepares and validates an atomic persisted-config update, sets the runtime listener to the new port, publishes the persisted update, and then reads back the provider listing, runtime listener, and file. If a crash or write failure interrupts that transaction, the next run compares all three surfaces and converges them to the provider's authoritative grant; a failure after the runtime change attempts to restore the prior runtime port when the prior grant still exists. A valid grant paired with either listener mismatch is a repair case even when no re-grant is needed.

On-box verification proves what the server can actually observe: the API request used the intended tunnel, the returned grant belongs to the configured allocation, the provider lists it, the provider tunnel is live enough for the API exchange, and the runtime and persisted listener ports agree. It does not call that an inbound end-to-end proof, because the site cannot validate its own external NAT path without a hairpin assumption. The change event asks the external vantage for a nonce-bearing probe when that facility is available, and rollout acceptance separately requires a roaming-vantage WireGuard handshake and application-level login.

The proposed timer runs every five minutes with a small per-host randomized delay and runs shortly after boot. The thirty-day lifetime alone would allow a much slower check, but the measured registry wipe was instantaneous and unannounced; five minutes bounds the ordinary unattended outage while keeping the operation to one cheap scoped listing. Randomization avoids making all servers re-grant in the same second after a provider-wide event, and a persistent timer catches a check missed during reboot.

Every mutation and every degraded result produces one structured journal outcome carrying the action or failure class, old and new grant generations when applicable, verification verdicts, consecutive-failure count, and total duration. Intermediate steps may add the same operation identifier, but success is represented by one final `healed`, `reconciled`, or `unchanged-near-retry` outcome rather than prose fragments. A normal healthy check remains quiet; a blind check, ambiguous listing, failed re-grant, failed local rebind, or failed read-back is loud and nonzero.

Idempotence is defined across provider, runtime, and persisted state rather than as “never issue the same command twice.” Re-running after a complete heal observes one valid grant and two matching listeners and changes nothing; re-running after a partial heal completes only the missing reconciliation. The script stores a provider-grant generation and endpoint-change digest so a service retry cannot emit duplicate letters for the same coordinates.

## Why a script, not an agent · `sec:doorselfheal:why-a-script-not-an-agent`

This loop has a fixed observation, fixed thresholds, a fixed transaction, and a fixed stop condition. The same successful listing and expiry value must produce the same result on every run, and failure must be apparent as a service failure rather than interpreted conversationally. Those are script properties: bounded execution, exact parsing, lockable state, repeatable fixtures, and machine-checkable exit codes.

The [resident server steward](resident-steward.md) occupies the other side of the boundary. A steward weighs workload intent, correspondence, evidence, reversibility, and policy when no threshold can decide safely; the door timer does not choose among providers, rewrite routes to invent a new path, contact support, move credential custody, or decide that an ambiguous API result probably means “missing.” It heals only the known shape that the programme has already authorized.

The proposed escalation threshold is three consecutive failed runs. At the five-minute cadence that gives a transient fault two automatic retries while making a continuing loss visible in roughly one quarter-hour. Each failed run remains loud in the journal; on the third, the script writes one root-authored degradation letter to owner correspondence and continues the same bounded check on later timer runs. It does not hand an agent the token or ask one to improvise recovery.

## Token custody · `sec:doorselfheal:token-custody`

The provider token already belongs in root custody on each root-full server because that server owns the allocation it must administer. The service runs as root, opens the existing root-only token file directly, passes the token only to the bounded provider request, avoids command-line and journal exposure, and never copies it into configuration, state, correspondence, a repository, an agent transcript, or the external beacon. No agent reads, transports, rotates, or renders the token; owner-controlled provisioning establishes it before the timer is enabled.

This custody argument depends on the server class. It is valid when the machine is an estate-controlled persistent root-full host whose threat model already admits an on-box root-only provider credential. A shared or ephemeral server on which policy forbids the token cannot run this loop as designed: moving the token there to gain convenience would erase the custody boundary the design is meant to preserve. That door needs a workstation-side owner, a later steward arrangement that can operate through the door without transferring the token, or an explicitly accepted manual duty.

## Change notification · `sec:doorselfheal:change-notification`

A re-grant normally changes the public endpoint port, so repairing the server alone can leave every roaming client aimed at the retired coordinates. The heal transaction therefore has two notification outputs. First, a structured `door-self-heal` journal event names the server identity, change digest, old and new port, grant expiry, verification result, and duration; a workstation capture tool reads this tag for the relevant lane's Sonnet watcher and treats endpoint change or degradation as wake-worthy machine content. Second, the service atomically installs a root-authored endpoint-change letter in the owner account's correspondence folder, naming the same digest and coordinates without any credential material.

Both paths are required because they serve different contracts. The journal is a low-latency signal and health stream, but retention and cursors make it a poor source of durable current state. The root-authored letter is the design-of-record handoff: it is stable, ownership-attributed administrative output that can be re-read after cursor loss, and its digest makes processing idempotent. The existing correspondence scanner correctly classifies that letter as admin output and should not wake a model merely because it appeared; the dedicated journal event wakes the workstation reconciler, which then reads the durable letter.

The workstation reconciler validates that the journal event and letter agree, rejects an older generation, updates the estate's private endpoint inventory, and atomically rewrites every workstation-managed roaming configuration registered for that door. It then verifies the new endpoint from an external path and records which independently held client packs still require delivery; third-party roaming devices receive a regenerated pack through their existing owner-controlled delivery channel rather than learning coordinates from the provider token holder directly. The server never reaches into client homes, and an unverified or partially distributed change stays visibly pending instead of being called complete.

## Out-of-band beacon · `sec:doorselfheal:out-of-band-beacon`

Each server also runs a small root-owned beacon timer that is operationally separate from the self-check service. The proposed sender transmits only an authenticated opaque server identifier, a monotonically increasing sequence, and a timestamp every two minutes to an estate-controlled external receiver. It binds to the ordinary site egress and must not traverse the provider tunnel, inbound forward, or provider API whose condition it is meant to distinguish.

The external receiver authenticates the touch, rejects replayed sequences, and stores the last accepted timestamp per server. A workstation-side beacon probe reads those ages from the working vantage and raises silence after three missed intervals, allowing ordinary jitter or one failed send without stretching diagnosis beyond a few minutes. Payloads carry no service inventory, tunnel coordinates, user data, or provider credential; presence, age, and server identity are enough. Any orchestration-side wait for these observations is a duty of the relevant lane's Sonnet watcher, not a session-side watching script (`proto:dispatch:log-eater-callback`).

A fresh beacon proves that the named server recently reached the independent receiver over outbound site connectivity; if its inbound door is unreachable at the same time, a complete site-uplink loss is ruled out. Silence from one server proves only that no authenticated touch from that server arrived inside the threshold, which could mean server, sender, route, site, or receiver trouble. Simultaneous silence from all co-sited servers while the receiver is independently known healthy isolates the shared-site failure class; it does not identify whether power, router, access line, or upstream routing is the component.

Independence is the beacon's value. Reusing the provider tunnel would make provider path failure look like site failure, and storing the only observation on the monitored site would make it unavailable precisely when needed. The receiver's own failure remains an ambiguity unless its health is separately proven or the vantage is redundant, which is an open decision rather than a reason to omit the first independent signal.

## Diagnosis order · `sec:doorselfheal:diagnosis-order`

The incident-derived runbook rule is strict: consult the external beacon vantage first, before changing workstation VPN exits, routes, DNS, WireGuard settings, or client endpoint files. If the receiver is healthy and site beacons are fresh, preserve workstation state and inspect the provider listing, self-heal journal, listener reconciliation, and external probe in that order. If all site beacons are silent, investigate shared site reachability and use an independent door; if the receiver itself is unhealthy, declare the diagnosis degraded rather than treating its silence as evidence against the site.

This order protects evidence. Workstation routing changes can create a second fault and erase the coincident path state that explains the first, while the beacon is both faster to read and outside the inbound path. Client-side experiments follow only after the vantage has placed the failure on the site, provider-door, or observer branch.

## Open questions · `sec:doorselfheal:open-questions`

1. **Who heals a tokenless ephemeral-pod door?** The options are a workstation-side mechanical timer that keeps the token in its present custody and performs provider calls through the pod's own tunnel, later steward ownership with the same no-transfer rule, or an accepted manual renewal and loss-recovery duty. The lean is a separate workstation-side timer: it preserves token custody and automates the known transaction, while acknowledging that it is not server-self-healing and inherits workstation availability; this proposal does not fold that different server class into the root-full rollout.
2. **Does renewal ahead of expiry retire the fixed monthly owner renewal?** The options are to make the timer the sole routine renewer immediately, retain a duplicate fixed owner action, or let the timer own execution while the owner audits results and retains a break-glass procedure. The lean is the third option, with the fixed monthly action retired after the deliberate-loss drill and first scheduled renewal both pass; duplicate routine renewal would race the same grant, while owner custody and review remain necessary.
3. **Should the beacon vantage be redundant?** The options are one receiver with independent health monitoring, two receivers in different failure domains, or cross-checking through another standing door. The lean is two independent receivers because one dead observer can otherwise resemble a dead site, but one externally monitored receiver should ship first rather than blocking the basic diagnosis correction.
4. **What external probe closes a heal?** The options are an on-demand nonce exchange driven by the beacon receiver, a workstation-owned roaming probe, or journal-and-local reconciliation followed by asynchronous probing. The lean is a receiver-driven nonce probe for immediate machine evidence plus a workstation roaming handshake for rollout acceptance; the former bounds automated uncertainty and the latter tests the real client path.
