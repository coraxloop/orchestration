# The security posture of the root-capable servers · `spec:security:root-server-security-posture`

Root-capable servers can apply a small set of deliberate configurations on top of Fedora Silverblue's defaults, producing a posture materially stronger than typical "hardened" server setups through a compact set of actions. This document records the argument for that posture — what the platform provides, what the model adds, precisely which attack surface moves, and what deliberately stays out of scope — so the posture is defensible from this page alone. The mechanics live in [confined-admin.md](confined-admin.md), the account classes in [the ratified model](proposals/root-server-account-model.md), and deployment-specific per-machine state belongs in a private server registry.

## What the platform provides, and where its defaults stop · `sec:security:what-the-platform-provides-and-where-its-defaults-stop`

A reference deployment measured Fedora Silverblue's defaults as strong in the places most distributions are weak: SELinux genuinely enforcing from first boot, Secure Boot honored end to end including real rejection of unsigned kernel modules, a minimal listening surface (sshd only, firewalld active, `PermitRootLogin prohibit-password`), and an immutable, rollback-capable operating system image.

The defaults stop where the assumed threat model stops: a single trusted human on their own workstation. Four gaps remain under this model; a reference deployment found and closed each during bootstrap:

- sshd accepts password authentication, so every password-bearing account is remotely guessable until keys-only posture is imposed per account or globally.
- Polkit grants any active console session machine-wide NetworkManager control — a public seat could sever the network, VPN included. (One trap measured in the reference deployment: NetworkManager answers "Already enabled" before consulting polkit, so enable-while-enabled is not a valid authorization probe; test with a connection-add.)
- Ordinary users are unconfined by SELinux on stock Fedora — the enforcing policy chiefly protects daemons. Universal confinement is an added control in this model, not a default.
- Convenience defaults with security texture: automatic suspend, session-level trust in the seat, and akmods happily delivering modules that Secure Boot will never load.

## Why universal staff confinement changes the surface · `sec:security:why-universal-staff-confinement-changes-the-surface`

Under the model, every account — the machine-owner agent included — runs `staff_u`; exactly one human rescue account is unconfined. The change does not shrink what a user may do with their own data; it shrinks what a compromised session can do to the system, and it converts administrative power from ambient to explicit. A reference deployment measured five deltas that carry the argument:

1. **uid 0 stops being admin.** Root inside `staff_t` cannot write `/etc` — observed as a failed sudoers write under a successful sudo. Hijacking a sudo-capable session no longer owns the machine; the attacker additionally needs the role/type transition (`ROLE=sysadm_r TYPE=sysadm_t`), a separate, journaled, policy-gated step. This is the single largest surface reduction in the model.
2. **Kernel module loading is label-gated.** Loading a correctly signed module from an unlabeled location fails with a bare `EACCES`; only `modules_object_t` sources are eligible. Unconfined users never feel this gate.
3. **Device access is label-gated.** Confined container domains could not reach the GPU device nodes (`xserver_misc_device_t`) until deliberately allowed; unconfined processes reach whatever discretionary permissions allow.
4. **Whole capability classes hang on enumerable role authorizations.** `staff_r` lacking authorization for `spc_t` made privileged containers structurally impossible until one `roletype` line granted exactly that ([the archived no-AVC bug](reference/bugreport-staff_t-container_t.md)). What a staff session may become is a short, readable list in policy, not an emergent property.
5. **Even management IPC distinguishes domains.** The rpm-ostree daemon refuses confined callers outright; system mutation is reachable only through the sanctioned wrapper path.

What confinement does not change, stated plainly: the user's own blast radius (a compromised staff session still reads that user's home, keys, and data, and has broad network egress), discretionary permissions (SELinux filters in addition to them, never instead), and kernel bugs (fewer reachable paths to attack surface, not fewer bugs behind it). One cost measured in the reference deployment is that universal confinement travels the policy's less-worn corners and finds its gaps — the container failure above surfaced with no AVC record at all, and flatpak does not function under staff confinement and was removed outright.

## Few states, all of them named · `sec:security:few-states-all-of-them-named`

The distance from stock defaults to the modeled posture is a short, explicit sequence of actions: a sudoers line with the role transition baked in, the confined default login mapping, one container-role CIL line, an sshd Match block, a polkit deny rule, a PAM `su` requisite, locked passwords on key-only accounts, a deployment pin before surgery, and the seat conveniences (auto-login, suspend-off) for the showcase.

The leverage comes from where enforcement lives. Conventional hardening accretes advisory layers onto a mutable system where root remains root — scanners, agents, and checklist sediment that a compromised admin session steps over. Here the substrate carries the enforcement (enforcing SELinux, Secure Boot, immutable image, bootable rollback ledger), and the actions merely choose its configuration: who is confined (everyone), who may transition (one journaled path), which doors exist (keys, physical presence, one forwarded tunnel port), and nothing else. Each action removes a class of state rather than adding a countermeasure — "root cannot write `/etc`" is a property of the domain, not a rule about attackers.

Two caveats keep this honest. First, reproducibility depends on preserving the discovery work: a reference deployment exposed dead ends — the sudoers chicken-and-egg, the silent container denial, the [kernel-module gauntlet](confined-admin.md) — and the durable asset is that the whole delta is recorded and replayable rather than folkloric. Second, the guarantee is scoped: system integrity and attributability, not total protection. A stolen loop key still acts as that loop; per-account data remains that account's to lose. What the model promises is narrower and stronger — no ambient admin, every privilege crossing explicit and attributable, and any surviving mistake one reboot from undone.

Log integrity is outside what the substrate guarantees, and the platform's own offer, journald's forward secure sealing, is declined rather than adopted: its verification key is the sealing seed, so the same key that checks a journal can re-seal a rewritten one, a leak is silent, retroactive and unbounded, and a passing verification upgrades a forgery into a proof-carrying record while inducing the reliance that shortens an investigation. The design that holds is the old one: a forward-secure signing key with a one-way step, each generation signing its successor, a sparse accumulator over the records with a signed root per interval and its commitment written in-band, the replica kept in a different trust domain so that no secret on the box can rewrite it, and an anchor outside the estate that cannot be retracted, because once an attacker holds the current key they can write any number of futures, and only a public commitment fixes the past.
